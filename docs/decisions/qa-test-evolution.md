# `/qa-test` and the QA pipeline — design record

> **Moved verbatim from `CLAUDE.md` §Detailed References on 2026-09-08** (PR 2 of the agentic-system audit). Every bullet here names its single source of truth in the first line; that file is normative, this record is the measured rationale behind it. Never loaded into an agent context.


## Cutting time-to-first-test

**Restructured 2026-09-10. Before it, a FULL run derived for four steps and only then looked at the product.** `1a` → `1b` → [`1c` ‖ `1d` ‖ `2-load`] → `1e` → `1e-plan` → `2a` → [`3a` ‖ `3x` ‖ `B`] → Artifact A (alloc, journey case, matrix assignment, authoring packs, a 3–4-way fan-out, serial appends, `suites:sync`, review/auto-fix) → the Step-3 hard-STOP verifier → *then* Step 4. The operator reported roughly an hour before the first browser touched the feature.

**Two costs, and the second is the one that mattered.** The obvious one is impatience. The real one is that **the run paid for the entire derivation before it could learn the derivation was pointless** — the module was not deployed, the env was unhealthy, the fixtures did not resolve. Every one of those ends in `BLOCKED`, and every minute before it was spent on a ticket nobody could test.

**The dependency graph already permitted the fix; nobody had read it as a graph.** The checklist execution consumes exactly two things — Artifact B and seeded data — and B is *"pure authoring off `1d`'s ACs"* while `3a` is browserless. It consumed **neither Artifact A nor the Step-3 verifier**, and yet waited behind both. So the restructure is mostly a re-reading, not an invention: **execution is triggered by a CONDITION — the checklist exists and its data resolves — rather than by a step number.**

**Four changes carry it.**

1. **`1r`, a reachability pass**, dispatched inside the existing `1c ‖ 1d ‖ 2-load` message: one agent, one lane, ~5 minutes, answering only *is there anything here to test*. It returns `REACHABLE` or `BLOCKED` and **is never evidence for `5c`** — a green `1r` is not a passing condition, and reporting it as one would be the reachability pass quietly becoming a test. On `BLOCKED` the run stops deriving immediately. This is the hour the change actually buys back.
2. **The DISCOVERY LANE moves ahead of the checklist, and the checklist is written from what it returns.** The first design tried the opposite — a thin checklist off `1d`'s ACs, executed before the model existed, with a second pass for the model's delta. It would have been faster and it was wrong, for a reason worth recording because it will come up again: **an early checklist is a shallower checklist**, and the failure this repo has already paid for is exactly per-screen checks that cannot notice the feature is broken (the Loyalty Missions numbers in `SKILL.md` §1). Defending against that needed a naming guard ("Reachable-path checklist (pre-model)"), a second execution pass, and a rule about which pass produced each verdict — machinery whose whole job was to compensate for the model not being ready yet.

   **Ordering it the other way deletes all of that.** `1e` → `3x` → `B` → execute. One checklist, one pass, no naming guard, and every item in it has been **seen** rather than inferred — because `3x` gained a **fifth routed output**: *conditions the ACs never named*. Before this the lane's findings reached Artifact A only, so the artifact that actually owns the verdict was the one written from a guess. **And `3x` is itself a live read of the product**, so the premise *"nothing touches the feature for an hour"* was never quite true and is now plainly false: the browser is on it at `1r`, and on it in depth from `3x`.

   **What it costs, stated because it is the thing the operator originally asked to fix:** `1e` and `3x` are back on the critical path to first *checklist* evidence, ~30-60 minutes of it. The trade was made deliberately — a simpler pipeline and a discovery-informed checklist, against a later first checklist run.
3. **The Step-3 gate splits.** `3-exec` (inline) checks the checklist's coverage, `td:validate`, and that named fixtures resolve *now* — and releases execution. `3-cases` (fresh verifier, hard STOP) keeps everything that needs the authored rows to exist, and releases C1. **This was not a new idea either:** the FAST gate had been exactly the `3-exec` subset all along, minus `suites:review`. The new disposition **`PENDING-A`** — *"this condition's covering case is still being authored"* — is legal at `3-exec` and **mandatory to close at `3-cases`**, which is what stops the split from losing a condition in the gap between the two gates.
4. **The duplicate execution of Artifact-A rows is removed.** The Step-4 specialist prompt carried the authored rows *and* C1 ran the same rows; only C1 emits the `RUN_ID` promotion needs, so the agent's copy grounded nothing. Every source described the duplication; none had ever justified it.

**What the restructure did NOT relax, because each rule cost something to learn.** `A` still waits for both `3a` and `3x` — cases authored beside the discovery lane are authored from exactly the guesses that lane exists to replace, and cases authored against unresolved fixtures produce the vacuous-pass shape the Loyalty Missions fixture set demonstrated. Appends stay serial with one `suites:sync` (a mid-write unparsable CSV blocked two sessions' gates for ~15 min). A verifier still never runs beside its own doer.

**The max-3 browser cap still holds by construction, and the priority order inverted.** `B` is written from what `3x` returns and `3-exec` gates on `B`, so execution cannot start while the lane is open — the structural guarantee survives. What is new is an explicit priority order for when lanes do contend, and its first entry is the counter-intuitive one: **`3x` > execution > visual > `1r` > C1.** Discovery outranks the verdict's own evidence not because it matters more, but because it is *upstream of the checklist that evidence comes from* — starving it stalls the whole run rather than one track. The lane's box also grew from a flat 25 minutes to a **scope-sized 30-60**, because a lane that now feeds the verdict-owning artifact cannot be tuned for one that only fed authoring.

**The uncomfortable part: this was designed against an unmeasured claim.** `summary.json.timing.steps.step1..step5` was **`0` in every file that carried the block, for the whole of its existence**, though `reporting.md` had always instructed filling it. The only end-to-end FULL datapoint in the repo is 215 minutes, 70 of it regression. So *"about an hour before testing starts"* was plausible and unverifiable, and the pipeline had been optimised twice already (the C2 move, then its removal) on numbers of the same quality. **Instrumentation is therefore part of this change, not a follow-up**: `steps.*` gets filled per step, and `time_to_first_test_minutes` — `started_at` to the `4a` dispatch — is the single number that says whether any of this worked. If it does not move, the restructure did not work and the record should say so.

## Removing 5r and 5g

**Both were removed on 2026-09-10, and the common thread is that neither answered the question the run was asked.** `/qa-test` answers *did this ticket pass*. `5r` answered *is the release safe*; `5g` answered *should the corpus adopt these cases*. Both are real questions with real owners — and both had been folded into a ticket run because that is where the evidence happened to be sitting.

**`5r` / C2 — the change-scoped Critical sweep.** ~24 runner dispatches, measured by the 2026-09-07 audit at **93% of a FAST run's tokens**. It never produced the verdict: `5c` derives that from atomic conditions, reconciled ACs, DoD items, `BL-*` and IN-SCOPE bugs — every one of them a claim about *this ticket* — while a Critical case failing in a neighbouring suite is, by `5a`'s own provenance rules, PRE-EXISTING or OUT-OF-SCOPE, and neither fails the ticket. So the pipeline spent ~40 minutes computing an input its own rules overwhelmingly discard. **It was narrowed twice before it was removed, and that history is the argument.** 2026-09-02 moved it off the critical path to *after* `5c`, which fixed the latency and kept the cost. 2026-09-09 made it opt-in on FAST, which fixed the cheap path and left FULL paying the bill on every run. Each narrowing was correct and each left the same defect one level up: **a step nobody had asked for, funded by a run that wanted something else.** The third narrowing is deletion. **Nothing was lost:** the sweep is the same `/qa-regression --cases critical` selection, run deliberately by whoever is cutting a release, and `regression:select` still computes its scope. What changed is who decides to pay for it.

**The one thing that had to be handled carefully is the Feature Release Gate.** `5e.1`'s *change-scoped regression ≥80%* criterion was defined on C2's pass rate. With C2 gone it ratifies as **`not-assessed` on every run** — and the rule that matters is the one written beside it: **never substitute C1's number.** C1 is the ticket's exact set and answers a different question; blending them is exactly how a gate reads GREEN on evidence nobody gathered. A criterion with no input is stated as un-assessed, which is the same *silence is never an answer* discipline the pipeline applies to sweeps, waivers and below-floor findings.

**`5g` — the `Draft → Automated` promotion flip.** Not a cost problem; a **placement** problem. Promotion is a write to the shared regression corpus, and it was sitting at the tail of a ticket run as a hard-STOP verifier gate that fired *after* the close-out had already been delivered — so it could neither block anything (the verdict was published) nor be skipped cleanly (it was a gate), and it added a fourth verifier dispatch to a run that was already over. It also created a second promoter: `/qa-test-lifecycle` Phase 6P promotes handoff, re-promotion and legacy sources, and two promoters for one corpus is one more than the single-writer discipline this repo applies everywhere else. **So `/qa-test` now appends its cases as `Draft`, executes them at Step 4, and stops.** 6P is the only promoter. The mechanism is unchanged and still documented at `skills/qa-test/promotion.md`; `tc:promote` / `tc:promote:apply` / `verify:gate --gate 5g` all survive, because 6P uses them.

**The cost of that, stated plainly:** a FULL run's cases now sit at `Draft` until someone runs `/qa-test-lifecycle VCST-XXXX --promote-only`, and a `Draft` case is one the regression selections do not treat as maintained coverage. That is a real gap if nobody runs it — the honest trade is that a corpus write deferred to a human is better than one made by a run whose own close-out is already delivered. **Watch for `Draft` rows accumulating**; `suites:lint` reports how much of the corpus has never run, and that number is the check on whether this was the right call.

**Labels are retired, never reused.** `5r` and `5g` are a citation contract; an older artifact citing either points at a step this pipeline no longer runs, which is the correct reading. `--release-regression` is gone with them.

## Domain maps

- **A DOMAIN MAP is the feature-scoped, persistent answer to *what is this thing and where are its surfaces* — `.claude/knowledge/domain/<name>.md`, shape at `.claude/knowledge/domain/domain-map.md`, built by `/qa-domain-map <slug>`, freshness-gated by `npm run domain:check`.** It is the counterpart to a per-ticket Test Model, and the two are deliberately different artifacts: a map is **feature-scoped and persistent** and answers *what exists, and where*; a model is **ticket-scoped and per-run** and answers *what could break here, and how would I know*. **A map never grounds an assertion as `{DOC}`** — it is a pointer index plus a surface inventory, and behavioural rules stay in `oracles/business-logic.md`. Confusing the two is the failure mode in both directions: a map carrying defect hypotheses becomes a stale test model, and a model carrying a surface inventory re-derives per ticket and evaporates.

  **This replaces the generated `functionality-map.md` (`map:refresh` / `map:check`), removed 2026-09-08 — and the replacement is not a re-run of the same idea.** That artifact was a **script-attributed index over documents**: it grepped the manifest, the suites’ `BL-*`/`ECL-*` citations, `@td()` aliases and config flags to answer *where is the prior art*, and its `Test object` block synthesised purpose/operations/variants from those same measurable sources. Two things killed it. **It could not enumerate a surface** — a script can grep a suite citation; it cannot walk an Admin blade and discover that `Lock` posts an empty body, or that the storefront has two org-switcher components on different markup. And **it corrupted its own artifact**: audit finding `D4` (2026-09-07) recorded that a fresh-clone `map:refresh` *“rewrote every prior-BA date”*, with `map:check` sitting RED among the drift gates. An index whose generator rewrites the dates that make its own staleness legible is worse than no index. **The domain map inverts every one of those choices**: one file **per domain** rather than one index over all 13 · **agent-enumerated live**, not script-attributed · **hand-curated with a per-claim verdict** (`CONFIRMED` / `DRIFT` / `MISSING` / `UNVERIFIED`) rather than machine-inferred · and **refreshed by an explicit operator command**, never rewritten as a side effect of a gate.

  **The measured incident that motivated it: VCST-5317.** A FULL `/qa-test` run tested one predicate (a locked membership) on one control (the desktop org switcher) with three verifier gates, a 17-scenario fault model and 34 authored cases — and never established the feature around it. Its context step read all **2,269 lines** of the domain’s nine prior-art BA deliverables **for the lock question and nothing else**. What that missed, established afterwards by one map pass: the feature spans **35 suites and 585 org-relevant cases** (the run believed ~18 suites, and missed `026` entirely — 53 of 53 org-relevant) · the storefront has **two** switcher components, and the run authored a case asserting the second one does not exist · **`selections.b2b` tests none of the Admin, GraphQL, auth or impersonation coverage** while running a suite with zero org content · roughly **200 cases have never been executed** · and the domain’s largest untested privilege surface is **three role-assignment paths reading roles from three different sources**, which the ticket’s scope could never have surfaced. The run’s own two real defects were found late, and the mobile one only because the operator supplied the navigation path.

  **Why a ticket-scoped step cannot fix this, which is the whole argument.** `/qa-test`’s `1b` `2-map` asks the right questions — purpose, operations, properties, variants, constraints — but it asks them **about the ticket**, so it inherits the ticket’s narrowness, and its answers live in one run’s working context. Every clause of the `1e` gate passes on a narrow chain: the matrix axes were correctly derived, no cell was blank, and nothing asked *is this chain a slice of a larger mechanism, and do you know the larger mechanism?* The map supplies that larger mechanism; **clause 11** makes the ticket state its chain as a slice, naming the links it touches **and the links it does not**, which is a positive statement someone can contradict rather than an assertion of completeness. **Clause 11b** requires every matrix variant to resolve to a real enumerated surface — the clause that would have stopped the false-premise case.

  **Superseded on FULL, 2026-09-10 — the recommendation became a BUILD, and only the recommendation changed.** The paragraph below is the original design and every clause of it still holds on FAST, and the *never-blocks* clause still holds everywhere. What it got wrong was the one prediction it could not test at the time: that an operator handed a good recommendation would act on it. Measured after ~2 months, the map existed for **1 of 13** domains — `b2b`, built by the run that invented the artifact. The recommendation is not badly worded; it is **badly timed**. It arrives mid-run, to someone who came for a ticket verdict, about an artifact whose payoff lands on a *different* ticket, and it asks them to spend a BA pass now for someone else's benefit later. Every individual decline is rational; the aggregate is that clauses 11 and 11b — the only two that catch a chain modelled too narrowly, the failure the other ten all pass on — were satisfied by writing `Domain map: ABSENT` on essentially every run, which is exactly the *"silence is never an answer"* trap in a new costume: the absence was written down honestly and nothing ever consumed it. So a **FULL** run whose domain is unmapped and whose chain is all-layer now **invokes `/qa-domain-map <slug>`** — the command itself, which dispatches `ba-system-analyzer` with its own Step-2 brief — at item `1c-map`, **inside the `1c ‖ 1d ‖ 2-load` message it was already sending** — the cost is a lane and a BA pass, once per domain ever, not an extra wave. Four things were deliberately NOT changed, because each is what keeps the promotion from becoming the *"both paths, always"* creep §Effort routing exists to end: **FAST is untouched** (it recommends, and the one-execution-agent promise holds); **`STALE` is never auto-refreshed** (a refresh rewrites a tracked knowledge file and must contradict its own previous rev — days-since-`generated` is a suspicion, not a mandate); **the all-layer trigger is unchanged** (a single-layer chain gets no build, and the trigger still reads the CHAIN, not the diff); and **nothing blocks** — a failed or gate-refused build records `build_outcome: FAILED`, leaves `state: ABSENT`, and degrades to precisely the behaviour described below. `disable-model-invocation` was **removed** from the command so the pipeline invokes the real thing rather than re-implementing its brief — a hand-rolled lighter brief produces a map that is not citable in the same shape as its siblings. The guard that matters was never the flag: it is `--refresh`, which **no pipeline passes** and which Step 0 enforces by STOPping on a fresh map without it.

  **And the other half of the same failure: a map that EXISTS was never updated either.** `1c` had always been required to report surfaces it touched that the map does not list, and a `D*` it confirmed or refuted live, and a `G*` it closed. All of it was routed as a **proposal** — the identical shape as the recommendation above, and it failed the identical way, because the only mechanism that could act on a proposal was a full `--refresh` nobody was going to run. So a run whose map exists now **writes back what it verified**, at `5h-map`: new §2 surfaces, a `D*` verdict moved in place, a `G*` marked `CLOSED`, a §4 count corrected. It costs **zero dispatches** — every fact is already in the run's artifacts. **Four constraints make the write safe, and each closes a specific way this could have gone wrong.** It runs **after 5f**, because clause 11b binds the matrix against the map's inventory and a run that widened the map first would be checking its own output. It writes **only live-`CONFIRMED`** facts — a `{HYPOTHESIS}` stays a proposal, because an optimistic claim in a map is precisely how a map does more damage than no map (shape gate clause 7). It **never deletes a row or renumbers an id**, since `D*`/`G*` ids are a citation contract; verdicts move in place. And it sets `amended:` while leaving `generated:` and `rev:` alone — **this is the clause that keeps `domain:check` honest**, because staleness measures the last full *enumeration*, and if amendments bumped `generated` then a domain touched every few weeks would never go stale and the one gate that catches a map describing a moved build would be silenced by a trickle of individually-true facts. Amending is not re-enumerating: it records what one ticket walked past, and says nothing at all about the surfaces nobody looked at.

  **It is a recommendation, never a gate, and the asymmetry is deliberate.** `1b` **recommends** `/qa-domain-map` when the scope is an all-layer e2e feature (api/graphql + back office + front) and no map exists; a missing map **blocks nothing**, because 12 of 13 domains have none and a hard gate would stop every ticket in the repo. `domain:check` fails on a **stale** map and passes on a **missing** one, for the same reason a stale map is the more dangerous artifact: it is read as current and arrives with a written deliverable’s authority. Where a map is absent the model records `Domain map: ABSENT — chain position unverified`, so **absence is written down rather than blocked** — the same *silence is never an answer* principle the pipeline already applies to sweeps and waivers, finally applied to its own context step. **The trigger reads the CHAIN, not the diff:** VCST-5317’s diff touched storefront + xAPI only, so a diff-based trigger would have stayed silent, while its value chain’s first link is *an admin locks the membership* — an Admin-layer action, and exactly where the two-step lock mechanism it tested blind actually lives.

  **Each run repays the map instead of only consuming it.** `1c` is briefed with the map path and **must report any surface it touched that the map does not list**; a `D*` row confirmed or refuted live becomes a verdict upgrade; a `G*` gap the run closes is marked `CLOSED` in place. `D*` and `G*` ids are a **citation contract** — updated in place on a refresh, never deleted or renumbered — and `ba-system-analyzer` is the **sole writer**, on the same single-writer discipline it holds for `business-logic.md` and the ECL.

- **Ticket status is one state machine with one owner — `.claude/knowledge/execution/ticket-status-transitions.md`, owned by `qa-lead-orchestrator`** (§Status custodian). The rules lived in two files with two different answers and a hole in the middle: `/qa-test` Step 4 said the opening hop takes *"no confirmation"* while `reporting.md` §5f titled itself *"with confirmation"*; the command's phase table mentioned neither; the 5f table had **two rows for a four-value verdict vocabulary**, so a **`BLOCKED`** run left the ticket parked in in-testing with no comment obligation and no rule, reading to everyone else as *QA is testing this* while nothing was; and the command still claimed 5h *"runs only after **a human** transitioned the ticket to TESTED"* when 5f is the pipeline doing it — a line `reporting.md` had already corrected in as many words. Now: **at most two hops per run**, the **opening** one at **`1a`**, the moment the `feature-test` route resolves (never confirmed — reversible, and the operator implied it by invoking the command; moved there from Step 4, because *in testing* means QA **owns** the ticket, which is true when the run is accepted rather than when the first browser opens — at Step 4 the board read the ticket as unclaimed through 30+ minutes of context, modelling, authoring and seeding, and only *this* pipeline was guarded against picking it up twice) and the **closing** one at 5f (**always** confirmed — terminal for the run, it notifies watchers, and `REOPEN` hands work to another team); the asymmetry is the rule, not an oversight. **Every verdict has a row**, and `BLOCKED` **transitions nothing but requires a comment** naming the blocker — `TESTED` would be a lie and `REOPEN` files an env/data blocker into the developer queue as though it were a product defect, the same mislabelling the 5d severity floor exists to prevent. **`qa-lead` is the only actor**: no specialist, runner, verifier, doer or sub-agent transitions a ticket, even while already in the tracker posting a comment — it reports up. Azure Boards now takes the **opening hop too** (its purpose was never only Jira reachability; it tells the board QA started), and every transition is still resolved **live** against `to.name`, never a hardcoded status name — including in `qa-lead`'s own Jira table, now labelled as this project's workflow rather than a contract. `--iterate` makes **one** closing hop at loop exit whatever the round count. What makes all of it checkable is the record: **`summary.json.status_transitions[]`** carries every hop **and every skip with its reason**, because before it a skipped transition left **no trace in any artifact**, so *"never moved"* and *"moved, note lost"* were indistinguishable afterwards.
- **`test-data-engineer` is now a CONDITIONAL step — `data_surface`, the fifth pre-flight axis (`1b` item 2f).** `3a` was an unconditional member of the Step-3 wave under a *"seeded env, green `td:validate`"* gate, and the only escape hatch was one sentence in `authoring.md` phrased *"skip **only when** every planned case resolves"* — **default-on with a burden of proof to skip**, so an opus agent was dispatched on runs whose cases resolved entirely against fixtures the environment already held. It is the one axis that **SUBTRACTS**: the other four ask *should we also do X?* (a `true` adds work), this one asks *does this ticket need data that does not exist yet?* and can only ever remove a dispatch — which is why it is **not** opt-in on FAST like `--visual`/`--contract`/`--coverage`, and derives and applies on both paths. It obeys the whole `axes.md` contract (derived, never asked, never defaulted; sources recorded even for a `false`; `unresolved` ⇒ `true`), and its sources are the `1e-plan` rows' own `@td()`/`{{VAR}}` refs → `td:validate` → the Part-0 value chain → the ticket/diff. **A `false` needs BOTH claims, not one** — the whole reason it is a token rather than a shortcut: the fixtures must *resolve* (deterministic, `td:validate`) **and** be *discriminating* on the links under test (judgment, `.claude/rules/test-data.md` §SECOND RULE). Loyalty Missions is the measured case for the second: every `@td()` resolved, every guard was green, and the seeded orders were flat $30 with no shipping, tax or discount — so *does the goal accrue `order.Total` or merchandise value?* was **undecidable from the data**, with both the right and the wrong implementation predicting `$30.00`. So a `false` is recorded **with the fixtures that cover the plan** (an unstated skip reads exactly like a satisfied seed); it fails **open**, because authoring against data that cannot answer the question yields BLOCKED cases triaged as product defects while a needless dispatch costs one browserless agent inside time the wave already spends on `3x` and `B`; and it gates the **dispatch**, never the **ownership** — a fixture need surfacing later still goes to `test-data-engineer`, never to an inline seeder. Record: `summary.json.test_data`; the Step-3 gate is now *"Artifacts reviewed + data **resolved**"*, and the verifier re-derives the skip rather than the seed.

Tracker-agnostic (normalizes type/status off `tracker-ops.md`). Consumed by `/qa-test`, `/qa-verify-fix`, `/qa-fix`, `/qa-hotfix-check`, `/qa-test-plan`. Read before any change to how a ticket picks its flow.
- **`/qa-test` is a command↔skill pair, not one file.** The command (`.claude/commands/qa-test.md`) is the **orchestration shell** — what runs, in what order, and the gate each step must clear; the **`/qa-test` skill** (`.claude/skills/qa-test/`: `SKILL.md` + `test-model.md` + `authoring.md` + `close-out.md` + `modes.md`, plus the shape in `.claude/templates/test-model.md`) holds the methodology and the measured rationale. Split 2026-09-01: at 1,044 lines it was the largest command in the repo and the only large one with no backing skill, so the pipeline contract, the methodology, the rationale and the worked examples were interleaved in one file — and a reader after "what runs at 5d" had to read past the Loyalty Missions evidence to find it. Same split as `/qa-design` ↔ `skills/qa-design/`. Two structural rules came out of it and are worth keeping: **the FAST path is stated once, completely, in one block** (it was 27 caveats scattered through FULL-path prose, so a FAST reader scanned the whole file to find the third that applied), and **everything after that block is the FULL path**. The command stayed normative and self-sufficient for *running* the pipeline — every gate's criteria are still in it, because they are the STOP conditions — while the skill answers *why*. `--epic` and `--iterate` moved wholesale into `modes.md`: two opt-in modes most runs never reach.
- **`/qa-test` is a tiered, gate-verified lifecycle** — Step `1a` **routes on two axes** (single source of truth: `.claude/knowledge/execution/ticket-routing.md`): first the **FLOW** by ticket **type × status** — a **fix-ready Bug** (READY FOR TEST/TESTING) is a *verification*, so `1a` runs `/qa-verify-fix` **RED→GREEN inline** (skipping the feature-test authoring/promotion machinery); a **hotfix-status Bug** → `/qa-hotfix-check`; a **Sub-task** → inherit its parent's type; everything else (Story/Task/Technical task/Epic, and a not-yet-fixed Bug) is a **`feature-test`**. Then, within `feature-test`, `1a` picks a **FAST or FULL path**, and the two now differ sharply in cost rather than marginally. **FAST is a checklist and nothing else**: a bug/tweak/config/tech-task that is P2–P3, single-layer and single-domain runs `1a`+`1b` → the Artifact-B checklist → one execution agent + the critical-case regression → `5a`–`5f`, with **no `1c`/`1d` agents, no `1e` Test Model, no archetype/UIP/`VC-*` sweeps, no case authoring, no `5g` promotion and no independent verifier**. The old split dropped only the two `1` agents and the verifiers while everything expensive stayed marked *"both paths, always"* — and 4 of the 5 recorded runs took FAST, so that was the path the cost sat on. Two consequences are deliberate: a FAST run **adds no regression coverage** (`/qa-test-lifecycle` is the way in), and its checklist is therefore the run's **only durable record**, which is why it is now a committed file. **FULL** — a new feature/Story/Epic, P0–P1, cross-layer, ≥2-domain, critical-revenue or unclear-surface ticket — runs the whole pipeline: `1c ‖ 1d` concurrent, **a mandatory Test Model**, full authoring, the three independent verifier gates, `5g` promotion. *When in doubt → FULL.* The **independent verifier runs FOUR times on the FULL path — Step 3, Step 5b, Step 5e and Step 5g, three of them hard STOPs** (5e's Feature-Release-Gate ratification re-derives the recommendation and does not hold the close-out; single source of truth for the count is the gates table in `.claude/commands/qa-test.md` §Quality gates — FULL path) — a **fresh `qa-lead-orchestrator` instance in §Verifier Mode** (`.claude/agents/qa-lead-orchestrator.md`), never the inline orchestrator and never the step's own doer: it re-derives evidence from source (re-runs `suites:review`/`td:validate`/**`tc:scope` with the same scope and risk terms**, and `npx tsx scripts/regression/compute-metrics.ts --gate feature --run-id <RUN_ID>` — **not** an npm script, and `--run-id` is mandatory or it returns the whole-history rate), re-opens evidence, delegates a live re-check on a **different browser lane**, returns APPROVE/REJECT, and on REJECT gives reason + fix → the doer fixes → **re-verify once (1 round), then STOP**. Every other step + the whole FAST path self-check inline. Gates: 3 *Artifacts reviewed + data seeded* (hard STOP) · 5b *Triage + AC/DoD vs implementation sound, incl. a quantified AC-coverage/DoD-completion estimate via `qa-metrics`* (hard STOP before verdict/filing) · 5e *Feature Release Gate ratified* (`skills/qa-metrics/quality-gates.md` §1a) · 5g *Promotion sound* (when new cases authored — runs last, non-blocking, after the verdict/report/status-change close-out). Human stays terminal (TESTED/REOPEN + a GO/NO-GO recommendation). The Feature Release Gate's pass-rate/bug math is deterministic via `scripts/regression/compute-metrics.ts --gate feature`. **The Test Model (Step 1e) opens with the VALUE CHAIN and is a fault model, not a scenario list.** **Part 0 is derived first** (`/qa-test-design` `test-design-techniques.md` §1a, token `FLOW`): the chain stated one line per link in the user's words (`trigger → effect → persisted state → the surface the user sees it on → what it unlocks`), **drawn** in Mermaid (a `flowchart` always; a `sequenceDiagram` when the chain crosses layers or any part is async; a `stateDiagram-v2` when the entity has a lifecycle or an effect is expected to reverse), the feature's **variants** (goal types / processors / role kinds — different code paths through the same link, so matrix rows rather than input partitions), a **variants × links coverage matrix with no blank cells** (a scenario # or `GAP`/`WAIVED + reason` — a blank is a hole nobody can see), and **reverse edges** resolved per forward effect on money/points/stock/entitlement (covered by #, or `ABSENT IN PRODUCT`, which is a finding to report). Parts 1–5 then build the fault model **per link**: a `Condition space` (factors × value classes + constraints), an explicit `Reduction` rationale (`N → M`, naming the dropped factors and what subsumes them), and a scenario matrix whose every row carries **cell · defect hypothesis · archetype · technique · oracle** — its **first row being the `Technique:FLOW` journey** that traverses the whole chain on the customer's own surface, authored first by Step 3 and titled `[JOURNEY]` — plus (when the ticket has one) a DoD checklist. **The order is the point, not the paperwork.** EP/BVA/DT/ST/PW/CT/EG are all parameter-space techniques: they refine a link that has already been named and none of them can name the chain, so run against an unnamed chain they faithfully produce per-screen field checks that are individually well-formed, strongly asserted, and collectively unable to notice the feature does not work. Measured on Loyalty Missions (VCST-5320/5346): **127 cases**, of which the 71-case storefront suite placed **zero orders** and 54 of its cases never left one page; the mechanism end-to-end (order → progress → completion → points credited) got **11%**; the last link — spending what the feature grants — got **one** case, written on the final day; **zero `BL-*` invariants existed for the domain**, so the corpus recorded behaviour instead of judging it; and no model was written at all (`reports/ba/test-models/` was empty). `npm run tc:rank` scored that storefront suite as *strong* (41 `INV`, 58 `KEEP`) — assertion strength says whether a check **can fail**, chain coverage says whether anyone **cares if it does**, and only the second one culls a garbage case (`qa-test-cases-generator` Step 3 §6d: a case that neither crosses a chain link nor guards one the journey crosses, and §6's companion rule that **no case may invert its assertion to certify a known defect** — that makes it green today, unfalsifiable forever, and red the day the bug is fixed). The archetype vocabulary lives in `knowledge/oracles/vc-bug-catalog.md` §Defect archetypes; technique tokens in `qa-test-design/test-design-techniques.md` §0. **The model's prose is still unlintable, but its scenario ROWS are now machine-checked before authoring.** Step `1e-plan` emits the matrix as an **authoring plan JSON** per target suite and runs `npm run tc:scaffold -- --plan <p> --check` (`scripts/test-cases/scaffold-rows.ts`), which **rejects a planned row that cannot answer the three §6d KEEP questions**: `observable` (the value it reads), `defect` (the failure a CUSTOMER would see — a **null-hypothesis** phrasing such as *"could fail to render"* is refused by name), and `plausible`, which must cite one of exactly the three grounds §6d allows — a `VC-*` catalog entry, a filed bug (`VCST-*` / `reports/bugs/…`), or `mechanism: <what in this code makes it likely>`. That is §6d's cull moved from *after* the candidate list is written to *before* it exists, which is the only place it is cheap: on the Loyalty Missions numbers it is the difference between writing 127 cases and writing the ones that matter, and it compounds into review, execution and maintenance in a way no amount of parallel authoring does. The same tool then **derives ten of the fifteen columns** from `(layer, priority, archetype, technique, ticket)` and leaves only `Preconditions`/`Steps`/`Assertions` blank — which `npm run suites:review` names per row as `S-006`/`C-001`/`C-003`, so the authored remainder is a linter-issued checklist. Its four **sweeps** (`state-stress` · `uip` · `toggle` · `date-range`) expand from the markdown that owns each table, **read at run time, never transcribed**, carrying that document's own pre-written defect hypothesis — so they clear the gate by construction, and a moved heading or reshaped table is exit 2, never a sweep that silently expands to nothing. It **never writes into `regression/suites/`**: output is a staged CSV in the scratchpad plus a `.design.md` sidecar recording why each row exists. The append gate is unchanged and still one step downstream: `append-test-cases-to-suite.ts` **rejects a new row whose `References` lacks `Archetype:<TOKEN>` · `Technique:<TOKEN>`** (vocabularies read at run time, never hardcoded; unreadable source ⇒ non-zero exit). It sees only new rows, so the legacy corpus is untouched. **Step 3b fans authoring out ONE BATCH PER EXECUTION SURFACE** — surface ≙ CSV file ≙ lane ≙ agent, so batches are file-disjoint by construction and the one-author-per-CSV rule stays literally true (deliberately NOT `/qa-coverage-generation`'s domain batching, which needs a "suite-write conflicts → merge IDs sequentially" repair pass because a manifest domain is not a file). Four things happen before dispatch, each closing a failure the fan-out would otherwise introduce: **`npm run tc:alloc`** scans the corpus ONCE and hands each batch a disjoint `--id-block` (`--check-global-ids` reads the corpus at *append* time, so two concurrent batches both pass it and then both write — and a cross-suite duplicate ID overwrites the other suite's per-case evidence at run time); the orchestrator authors the **`[JOURNEY]`/`Technique:FLOW` case itself** and puts it in every brief (it crosses every layer by definition, so per-layer batches each writing their own produce N partial journeys and no owner of the chain); **every blank matrix cell is resolved and each cell assigned to exactly one batch**, which makes duplication structurally impossible and removes the need for a cross-batch dedup pass; and each brief carries a compiled per-layer **authoring pack** (extracted rule text + that batch's rows + the journey + selectors/schema fragments) because four agents re-reading the same oracles is 4× the dominant token cost for zero extra information. Batches self-lint their staged CSV to green and return a path; the orchestrator appends **serially** and runs `suites:sync` **once** — `suites:lint`/`sync` hard-fail on a parse error anywhere in the corpus, so N parallel writers into `regression/suites/` would multiply a tree-wide outage by N. **The same gate also enforces assertion STRENGTH (`T-006`)**: a case whose every assertion is presence-only (`visible`/`shown`/`present`) is rejected, because such a check fails only when an element is absent entirely — the rarest failure mode — while real bugs render *something* (the open `non-usd-price-zero-display` renders a literal `£0.00`, so "price is visible" passes). `npm run tc:rank` reports the current share; no figure is transcribed, because the first version quoted one the next commit invalidated and it went stale in four places at once. The ladder is `INV` (measured invariant) > `REL` (a relation between two observations) > `DER` (against an `@td()`-derived value) > `SHAPE` (format/order/count) > `PRES` (guard only); `INV`/`REL`/`SHAPE` are literal-free, which is what makes them the third path out of the squeeze between `GRD-002` (no invented literal) and `DV-016` (no hardcoded value) that had left `PRES` as the only legal form. Corpus-wide `T-006` is an Informational file-level tally (a per-case High would flag ~1 900 cases on day one and push everyone to `--warn-only`). Storefront cases get a first-class measurable vocabulary — `[VIEWPORT] [SNAP] [PROBE:*]` → `[SHIFT] [TOUCH] [SPACING] [ALIGN] [OVERFLOW] [CLS]`, already implemented in `layout-runner.ts` with derived thresholds and running in `048c`, but previously undocumented and unreachable from authoring, so every generated UI case degraded a measurable invariant into prose. `modern-web-attack-surface.md` now carries the closed **`UIP-*`** probe set (Back after submit · deep link · refresh mid-flow · two tabs · expired session · corrupted storage · blocked dependency · autofill · zoom · data state), swept like archetypes — the corpus had 8/5/11/5 of those across 1 961 Frontend cases while the matching bugs sit in `reports/bugs/open/`. **The Test Model is a durable file** at `reports/ba/test-models/<TICKET>-<date>.md` (`reports.md` category 3, 60–140 lines), **written on the FULL path only and required there** — it is what makes a story's context understandable and its documentation adequate, a need a P2 config tweak does not have. A model nobody can re-open cannot be argued with, and a surface's parameter model is reused across tickets. Its prose is *intended* to be lintable, but **`npm run model:lint` is not implemented** — do not cite it as a live gate. The two deterministic gates are `tc:scaffold` over the plan (before authoring) and the appender (before the CSV). **`npm run tc:rank` / `tc:demote`** are the missing counterpart to the one-way `promote-cases.ts`: ranking by assertion strength and step cost (not by yield — that is still not computable), and demotion to **`Manual` only**, never `Deprecated` (TRI-006 keeps deprecation human) and never deletion, guarded so a Critical/P0, a cheap, a deliberately `Archetype:`-stamped case, **a case the classifier cannot read**, and above all **a case `tc:yield` proves has caught a real bug** are always `STRENGTHEN` and never demoted — a code review found the ranker demoting 10 of the 36 proven catchers, including the tests that caught a nested-impersonation privilege escalation and a stored XSS, because the one piece of ground truth in the repo was never consulted. `UNKNOWN` is reported separately from `PRES` throughout: a gap in the classifier's vocabulary is the classifier's problem, never evidence about the case, and conflating them had put 158 candidates (117 Backend, incl. live cross-org authorization tests) on the demotion list. **`npm run tc:yield`** closes the loop that made all of the above a prediction rather than a measurement: `scripts/lib/defect-attribution.ts` parses the `**Found by:**` / `**Case:**` provenance out of `reports/bugs/**` and joins bug → case → suite → run, so "has this case ever caught a bug?" is answerable (baseline the day it shipped: **36 of 4 185 cases, 21 of 128 reports name a case**). `bugs_found` is **derived at read time** in `compute-metrics.ts`, never stored — the bug report is the source of truth, it is durable while `history.json` prunes at 90 days, and a stored count goes stale the moment a bug moves `open/`→`fixed/`; that alone took `defectDensity` from a flat 0 (populated in 0 of 109 rows) to a real number. The parser **validates every id against the real corpus** because the prose it reads carries `BL-AUTH-009`, `VCST-5504` and `AC-2` in exactly the position a case id appears — a parser trusting shape would manufacture attributions and make the metric that judges this work unfalsifiable; a case-shaped id that does not exist is reported as a broken audit trail, and an unattributed bug is recorded by source (it is signal about where cases *aren't*), never dropped. First read, and it is weak evidence, not proof: cases credited with catching a bug carry a discriminating assertion **77%** of the time against **58%** for the rest of the corpus — n=30, drawn almost entirely from one run, observational and open to reverse causation. This is the artifact `test-management-specialist` authors cases from in Step 3. **And the model is now EXPLORED before it is authored against — Step `3x`, the discovery lane, FULL path only.** The pipeline derived for four steps and never looked at the running feature until Step 4 executed cases that were already written, so the model's `{HYPOTHESIS}` oracles, its `GAP` matrix cells, its unresolved reverse edges, `1d`'s DRIFT/NOT-FOUND/CONTRADICTS ACs and Step-2a's `RE-BASE` rows all reached authoring as guesses — three of those five being promises the pipeline had already made to *verify live* and never scheduled. `3x` **invokes `/qa-exploratory ticket <ticket-key>`** (that command's new third charter mode, its Step 0b; `disable-model-invocation` was removed for it, because a pipeline step nothing may call is a step that never runs — which is precisely how a fully-built discovery capability, 10 techniques and a charter library and the ECL/BL supply axes, came to sit at **one** session in the life of the repo). The division is one line: **this pipeline supplies the CHARTER, that command runs the SESSION** — deliberately NOT the visual lane's pattern, which dispatches `ui-ux-expert` and is told never to invoke `/qa-design` because `/qa-design` is only a shell over the same agent, whereas `/qa-exploratory` is where the substance lives (the subtract/supply oracle split, the `[THEORETICAL]`-first ECL rule, the surprise-seeking box, the personas and tours, the non-firefox lane rule, the `Fate` capture-back contract, the report shape `/qa-review-oracles` reads). The charter is **derived from those five sources and nothing else**, and `ticket` mode **STOPs without a model** rather than improvising a mission — the same anti-hallucination discipline `sprint` mode already applies. It runs **concurrently with `3a`**, which is free concurrency rather than a stolen lane (`test-data-engineer` is explicitly browserless, so the session's one chrome/edge lane is the only one in use), in a hard **25-minute** box, and it **closes before Artifact A**, which is the whole point: its four outputs are *inputs to authoring*. Those outputs are each routed to a named consumer — **model amendments** (amend the existing `<TICKET>-<date>.md`, never fork it, the `--iterate` rule) · **`{HYPOTHESIS}` → `{OBSERVED}` grounding per row**, which is the biggest quality win because a row whose oracle was observed gets an assertion that can be *graded* where the same row authored blind gets a presence check or a hypothesis `GRD-001` escalates to Blocker at 5g · **net-new scenarios with a `Fate`**, where `PROMOTE` means authored **in this run** rather than deferred to a later sprint (the difference from a standalone session) · **Oracle Feedback** as `/qa-review-oracles` proposals, never edits. **The lane files no bugs** — findings enter 5a's triage with everything else and take an ordinary provenance, usually PRE-EXISTING since it explores adjacent ground, which is not a reason to discount them because a PRE-EXISTING bug found *before* authoring still changes what Artifact A asserts. It **never blocks**: the box is hard, Artifact A proceeds on what returned, but every charter source is **covered or `NOT REACHED + reason`**, a skip is stated, and `summary.json.discovery = null` means the lane never ran while an empty array means it ran and found nothing — different facts. **FULL only, stated rather than implied**: three of its four outputs consume a Test Model and an authoring batch and FAST has neither, the fourth is `/qa-exploratory`'s own job on any path, and the visual lane's argument for breaking FAST's one-agent promise has no analogue here. Round 1 only under `--iterate` — the model is amended rather than re-derived, so a round-2 session would explore a surface whose unknowns have not moved. Single source of truth: `.claude/skills/qa-test/exploratory-lane.md`. **Two ordering fixes ship with it, both pure latency:** the domain-keyed oracle TEXT (`2-load`) consumes nothing `1c`/`1d` return, so it is loaded in the same message that dispatches them rather than a full wave later (only the VirtoOZ gap-fill, `2-topup`, is genuinely downstream); and `tc:scope`'s SCAN moves into `1b`'s wave B where the SKILL's own concurrency table already put it, while its four-value DISPOSITION stays at Step 2a where the loaded `BL-*`/`ECL-*` text makes it judgeable — scanning and disposing were being treated as one step, which cost a round-trip for a ~1 s read. **Test cases are one pipeline shared with `/qa-test-lifecycle`, not two:** Step 3 **reuses the same skills** lifecycle Phases 3–4 use (`/qa-test-cases-generator` + `/qa-review-tests` + `/qa-generate-data` — neither command restates a dimension, code, column or enum; `/qa-test` does **not** spin up the full lifecycle command), and **appends new cases directly into `regression/suites/<layer>/<module>/*.csv` as `Automation_Status = Draft`** (the runner does not skip Draft, so Step 4's regression executes them — the "latest test"). **That regression is case-scoped, time-boxed, and now SPLIT IN TWO, only one half of which gates the verdict**: **C1** — `/qa-regression <suites> --ids <the new Draft ids + every Step-2a RE-BASE id>`, an exact set answering *did this ticket's cases pass* — runs at Step 4; **C2**, the `--cases critical` sweep over the `regression:select --target 40` suites, answers *did the change break anything else*, which is a **release** question consumed by the Feature Release Gate, and moved to the new **`5r`**: launched the instant 5c is recorded, overlapped with 5d and drafting 5e. This is the largest cut to verdict latency in the pipeline, and it follows from 5c's own table — atomic conditions, reconciled ACs, DoD items, `BL-*`, IN-SCOPE bugs are every one of them a claim about *this ticket*, while a Critical FAIL in a neighbouring suite is PRE-EXISTING or OUT-OF-SCOPE by 5a's provenance rules and fails nothing, so ~40 minutes sat on the critical path to a verdict that discarded its result. **5c RECORDS the verdict; 5e PUBLISHES it** — that gap is what makes the move safe, because an IN-SCOPE C2 finding **amends** the recorded verdict once (5c's existing table, no new criteria, then STOP) with no comment to correct and no transition to reverse. `--also-ids` leaves this pipeline with it — it existed only to smuggle the run's own cases into a tier sweep, and they now have a run of their own — surviving in `5k`'s C2, which reached the same two-track split first and is now named in these terms. A skipped C1 (no new cases, no `RE-BASE`) and a skipped C2 are each **stated**, since an omitted regression track reads exactly like a passing one. Selecting whole *suites* is what made a search-change run plan all 44 cases of suite `004` (6 Critical, 19 skipped); Critical is 918 of 4,243 cases (~22%) and ~23% of the estimated minutes, which is what puts a single-module change inside a **40-minute window**. The filter is `npm run suites:filter` (`scripts/regression/filter-cases.ts`), applied by `regression-orchestrator` Step 3a at the existing per-suite resolved-CSV hop — so lanes, machine lane, merge, triage and promotion are untouched. **Nothing is dropped silently**: the run report carries a Scope Exclusions section naming every suite that contributed zero cases (11 of 128 hold no Critical case at all), every unreadable `Priority`, and every legacy-header refusal. `--target` trims by predicted **makespan** and never trims the risk floor, but its `estimatedMinutes` input is documented as wrong by ×18–×88 for runner-native suites, so the run **states the prediction and the exclusions** rather than trusting them — and `summary.json.timing` now records predicted vs actual so `regression:recalibrate` eventually has ground truth. FAILs are triaged at Step 5a via **`/qa-triage-results <RUN_ID> --fix`** — reusing that command's deterministic collect + classify + live-verify + test-case auto-fix + flakiness-history feed instead of re-deriving the taxonomy ad hoc). Confirmed bugs are filed at Step 5d with a **tracker relationship by provenance**: IN-SCOPE → a **Sub-task of the ticket**; PRE-EXISTING → linked only, never re-filed; OUT-OF-SCOPE incidental → its own standalone ticket + related link (unchanged). **5d also applies a SEVERITY FLOOR — `Critical`/`High`/`Medium` (P0–P2) file, a `Low`/P3 does not**, for either shape (no Sub-task, no standalone ticket). A below-floor finding is dropped from the **tracker**, never from the **run**: its `reports/bugs/open/` draft stays, the 5e tracker comment carries a mandatory `Not filed (below severity floor)` line that reads `None` when there are none (an omitted line is indistinguishable from a clean run), `summary.json.bugs_not_filed` records it, and on FAST the Artifact-B checklist carries it too since that file is the run's only durable record. Severity is 5a's call, already ratified by the 5b gate — 5d applies the floor and never re-grades to move a finding across it, which is the one move this rule must not induce. Below-floor findings are also outside `--iterate`, since `/qa-fix` needs a filed ticket. The tracker **comment is posted before the status transition** (Step 5e, then 5f) — two distinct actions. Promotion is **in-run at 5g, last and non-blocking**: Step 4 grounds `{OBSERVED}` via the automated regression runner, then 5g (ratified by the fresh `qa-lead` verifier re-deriving G10 + user confirmation) flips each eligible case **`Draft → Automated`** via `npm run tc:promote:apply` (green under the automated runner — it writes `Automated` **only**, and only onto a row that is exactly `Draft`; `Reviewed`/`Manual` remains a human call it never makes), **reverts non-promotable rows**, and leaves a case that failed on a real in-scope bug at `Draft` with a reason. `/qa-test-lifecycle` Phase 6P remains the promoter for handoff / re-promotion / non-`/qa-test` sources. **`--iterate` (default `--max-rounds 2`) turns the Step-5 close-out into a bounded test → fix → re-test loop (Step 5k):** a FAIL auto-runs `/qa-fix` (G0–G7, never merges) → `/qa-deploy-pr` deploys the **prerelease** (confirm each deploy — the loop always re-tests an *unmerged* build, so the §2 never-auto-merge guard is never touched) → then, **at the head of every round (`5k.0`)**, probes the deployed build and **re-reads the board** — the ticket's sub-tasks and linked bugs, classified live, each fix-ready one verified by an **inline `/qa-verify-fix`** (never inferred from a case going green, which is the only way a bug with no covering case — every bug a FAST round files — can be verified at all), a VERIFIED one hopping to **`TESTED` only when its fix is MERGED and present in that probed build** (green on the loop's own unmerged prerelease stays comment-only; either half UNKNOWN ⇒ no hop; `FIX_INCOMPLETE`/`INTERMITTENT`/`NEW_REGRESSION`/`BLOCKED` defer their `REOPEN` to loop exit so a sub-task is not flapped out of in-testing N times) → **and only then** re-runs the failed cases / checklist items + change-scoped regression, up to the cap, then STOP for a human; PASS exits to the Feature Release Gate. Merge + release always stay the human's. Without `--iterate` the close-out is pointers-only (state the next command and stop). **The loop was specified by what it RE-RUNS and silent on what it RE-PERSISTS, and that silence was the defect**: read literally, round 2 filed no bug — so a round-2 FAIL had no ticket for `/qa-fix`, dead-ending the loop at its own precondition — wrote no verdict into the committed checklist (the FAST path's *only* durable record), never reached 5g, and had nowhere to record a round (every `summary.json` field except a 4-key `iterations` counter is single-valued, so round 2 silently overwrote round 1's verdict, counts, `regression.run_id` and timing while `modes.md` demanded "a per-round summary" no artifact could hold). `modes.md` §5k now carries a **per-round assignment table with a reason per row**: 5a–5d + a round-delta comment + `summary.json` + an **append-only** checklist section run **per round**; the Feature Release Gate, the full QA-Complete comment, the tracker transition and promotion run **once, at loop exit** — so a `--iterate` run makes ONE transition and posts ONE QA-Complete comment whatever the round count. Three rules make it coherent: a bug this run already filed takes a third provenance, **CARRIED** (keeps IN-SCOPE + its severity so it still fails 5c, files nothing, one comment on its existing Sub-task — where PRE-EXISTING would have said *don't fail this ticket* about the ticket's own Sub-task); a carried bug that goes green is commented and recorded but **deliberately not transitioned**, because the fix is an unmerged prerelease and nothing has shipped; and 5g promotes **per `RUN_ID`, `--ids`-scoped to the cases that run executed**, because `tc:promote` can never re-promote, so a round-1 flip is irreversible and would ground `{OBSERVED}` in the build that was wrong.
