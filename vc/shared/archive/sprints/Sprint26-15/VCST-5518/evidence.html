Why this is reopened rather than passed

The reported defect is genuinely fixed and proven three times over — the working coupon survives, and the evidence below stands. But the interaction the fix produces ends in a bad state: the “This code is not valid” error never clears, so the shopper is left with a permanent red error on a cart that is completely healthy.

couponError is declared at module scope, outside the composable, so it is a singleton that outlives the component. Its only reset is clearError(), invoked at the top of applyCoupon / removeCoupon. Consequently:

  • Typing a new code, blurring the field, and the cart updating all leave the error on screen.
  • Navigating away from the cart and back leaves it on screen — module state survives unmount.
  • It only disappears when the shopper applies or removes some other coupon, or reloads the page.
  • clearError is exported, but no component destructures or calls it — the UI never invokes the one reset that exists.

Pre-existing, but newly load-bearing. This code is byte-identical on dev and on the fix branch, so the fix did not introduce it. Before, the invalid apply also mutated the cart, so the error accompanied a real state change. Now nothing changes — a stale error is the only outcome the interaction produces, which is what makes it worth fixing here rather than deferring.

Suggested minimal fix: wire the already-exported clearError into the custom-code input's @input, and clear on unmount — or move couponError and loadingCouponCode inside useCoupon() so they cannot outlive the component.

The reported defect — what was wrong

Replacing a coupon was remove-then-validate with no rollback. applyCoupon() removed the working coupon first, then validated the new code — so when the new code was invalid, the function returned early having already thrown the discount away. The shopper saw only “This code is not valid”, which reads as the new code failed, never your existing discount is gone.

The fix moves validateCartCoupon() ahead of the removal, so an invalid code exits before any mutation is issued.

The root-cause proof is an absence. RemoveCoupon is gone from the wire entirely — the whole invalid-apply interaction is now a single request. This is the strong fix variant: the mutation is not issued-and-undone, it is never issued. A rollback-style fix would look identical in the UI but would still show the remove/re-add pair here.

Notes carried forward

Reopened, not passed. The checklist above covers the reported defect only. The stale-error behaviour at the top of this page is what sends VCST-5518 back rather than to Tested — the fix changes this interaction, so it should leave a clean end state.

The deploy pin is temporary. The environment was repinned to the PR artifact for this run and should be reverted once a normal build carries the fix. vc-frontend#2422 is still open.

The ticket's readonly note is wrong on this build. The Custom-code input stays editable while a coupon is applied — and that typed path drove all three runs. Triangulated separately as oracle drift, not a defect: BL-CART-009 has been corrected, because the real binding locks that input only when its own value equals the applied code. Its Apply button is disabled when the typed code duplicates a rendered preset card, independent of applied state — which is why check 6 has no reachable path.

Pre-existing, untouched: [Vue apollo] useQuery() is called outside of an active effect scope still fires about once per coupon interaction on this same surface. Present before the fix, unchanged after. Not filed.

Coverage gap: BL-CART-009 is cited by no test case. This scenario is now reproducible as passing behaviour and is worth a regression case in the coupons suite.
