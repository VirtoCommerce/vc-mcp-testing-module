VCST-5802·Bug · Medium·WCAG 4.1.2·2026-09-02

VcScheduler: the event quick-info popover had no role and no accessible name

VERIFIED WITH NOTES STR 3/3 · 13 pass · 1 not-run · 0 fail

The defect

The popover opened by clicking an event chip rendered as a bare div.vc-popover with role = null and aria-label = null, and focus never entered it. Escape did close it and focus was on the chip afterwards, so there was no trap — the gap was role and naming plus focus entry.

The same .vc-popover component had already been given a dialog role and a localized name for the “+N more” overflow popover under VCST-5671, but at the overflow call site rather than in the shared component — so the quick-info call site still carried the original gap.

Fix under test

PR #350 gives all three anchored popovers role="dialog" and an accessible name, and moves focus entry/restore out of the overflow popover into a shared useAnchoredPanelFocus. Dialog semantics stay opt-in props on VcPopover — three call sites opting in, not a change of default.

Item 6 is NOT-RUN, and deliberately not assumed.
The “Event details” fallback could not be exercised: quick-create's Save renders disabled on an empty title, the editor modal shares the same non-empty-title guard, the documented EmitMode empty-title path rendered no event at all, and no fixture ships an untitled event. It is unit-verified (RED-A covers it) and browser-unverified — which is exactly what keeps this run off a clean VERIFIED.
* Item 8 — the expectation in the brief was wrong, not the product.
The brief said the overflow popover is named by the formatted date, taken from the dev's own comment. It is actually aria-label="$t('VC_SCHEDULER.MORE_EVENTS')" → “More events”. Settled by diffing MonthMorePopover.vue at #349 against main: the name is identical at both, so #350 did not change it and VCST-5671 is not regressed — its focus entry and restore-to-“+1 more” still work too.
† Item 14 — axe is blind to this defect, so its clean result proves nothing here.
axe 4.11.3 loaded (no CSP block) and returned 0 violations, 0 incomplete and 14 rule-passes scoped to .vc-popover. But the pre-fix bare div would likely have scanned equally clean: axe cannot see a missing role on an element with no interactive semantics to contradict, nor a focus transition that never happens. Recorded as non-regression cover only, never as evidence the defect is fixed. The a11y tree and the focus probes are what carry this verdict.

Findings not filed

  • Escape from quick-create leaves no focused element. Its opener is a non-focusable day cell, so a keyboard user is dropped to <body>. Pre-existing and not a #350 regression — pre-fix it had no focus management at all. Worth noting that this is the same defect class as VCST-5813 (focus dropped to body with no repair target), so it may belong with that line of work rather than filed alone.
  • The Loading story nests ~40 role="status" live regions inside an outer status "Loading events…" — a plausible announcement storm, unverifiable without an assistive-technology pass.
  • The overflow popover's accessible name overrides its visible date. aria-label="More events" replaces the visible date header, so a screen-reader user loses the date a sighted user sees — the same class as VCST-5803's 24-hour/12-hour chip mismatch. Out of this ticket's scope, and it is also why the dev's comment describing that name as “the formatted date” is inaccurate.
Oracle substitution. vc-shell is a separate product: BL-UI-*, critical-ui-scope.md, storefront-selectors.md and the suite manifest cover nothing here. BL-A11Y-001 and BL-A11Y-003 are inapplicable by their own rule text, which scopes them to “the accessibility-gated storefront themes”. BL-A11Y-002 (accessible naming) and BL-A11Y-004 (role/state correctness) are stated product-neutrally and are the subject matter, but all their Source and Suite coverage evidence is storefront (client-app/, suite 045) — so they are cited by analogy only. Primary oracle: WCAG 4.1.2 Name/Role/Value plus PR #350's own documented contract.
