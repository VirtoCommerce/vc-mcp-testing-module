# VCST-5673 — deploy gate + THE SPLIT (this ticket is two halves in two repos)

## 0. Why this ticket is not an ordinary verify-fix
The reported symptom — Escape / Ctrl+I inert while the chat holds focus — is STRUCTURAL, not a
listener bug. A keystroke goes to the document owning the focused element; the panel is a
CROSS-ORIGIN iframe; a cross-origin parent cannot observe those events by any means. So it needed
a RELAY, and the work split across two repos:

  half 1 — vc-shell (ours)      : accept a CLOSE_PANEL message, and accept it only from the right sender
  half 2 — virto-oz (the chat app): forward its own Escape / Ctrl+I as
                                    window.parent.postMessage({type:"CLOSE_PANEL"}, <shell origin>)

On 2026-08-12 the fix author asked QA explicitly NOT to retest before half 2 shipped — "rather than
retesting against the shell build and finding it unchanged". That warning was correct then. It no
longer applies (see §3).

Also corrected by the author, and worth carrying: the ticket says "the iframe capturing focus is
correct for a11y", implying the shell focuses it. It does not — there is no focus() call anywhere in
the ai-agent plugin. The CHAT autofocuses its own input on load.

app's TOP-LEVEL window — a postMessage from a nested frame inside it is now rejected.

The failing sets are DIFFERENT, and each is exactly its own half:

  RED-a fails the NEGATIVE path — the guard #305 added:
    x ignores CLOSE_PANEL from a window that is not the registered chatbot iframe
    x rejects forwarded messages from another window at the same origin

  RED-b fails the POSITIVE path — the capability #292 added:
    x closes the panel when an allowed origin asks it to
    x accepts forwarded messages from its parent window

Logically consistent: with CLOSE_PANEL absent altogether (RED-b) the negative tests pass trivially,
because nothing is honoured from any sender. #292 added the capability, #305 added the guard, and
both are independently pinned.

## 5. What a verdict here can and cannot rest on
Half 1 is verifiable by us and is verified (§1, §2, §4). Half 2 is another repo's code running in a
separately deployed app — the only way to confirm it is the live STR. If the live STR fails, that is
NOT a vc-shell defect and must not be recorded as one: it would mean virto-oz#17 was closed without
the relay reaching the deployed panel. Report it that way, precisely.
