## 5. WHY THE TOASTS ACTUALLY COLLAPSE — and where the fix's own reasoning is wrong
The interceptor's code comment claims:
   "All of them fail with the same error, so a consumer that does surface it shows one message,
    not one per request."
and useAsync.docs.md claims:
   "...this suppression and the notificationId de-duplication both collapse them to a single
    toast at most."

Traced both mechanisms:

  MECHANISM 1 — REAL, and it is the whole story.
    framework/core/composables/useAsync/index.ts:64
      if (shouldNotify && !isSessionExpired() && e && typeof e === "object") {
    While the latch is engaged useAsync does not notify AT ALL. So the 4 parse-error toasts become
    ZERO, not four identical ones — stronger than the docs' "a single toast at most".
    This guard is PRE-EXISTING (not added by #291).

  MECHANISM 2 — DOES NOT EXIST as described.
    notifications/notification.ts showNotification() ALWAYS calls _backend.appendInstance(options),
    and when no notificationId is supplied it GENERATES A FRESH ONE (:49-52). There is no add-time
    dedup. hasNotification() exists but is never used to guard an add (only useContainer defines
    and re-exports it). The container's appendInstance only mounts a per-position container — no
    content or id dedup either.
    => N calls without an explicit notificationId produce N toasts. "notificationId
       de-duplication" only applies when a caller passes the SAME explicit id, which nothing on
       this path does.

Consequence: the fix WORKS, but not for the reason its own comment gives. The claimed safety net
("same error -> one message") is absent. Any consumer that surfaces the rejection WITHOUT going
through useAsync — calling notification.error(...) directly — would still get one toast per
request. Behaviour is correct today because every burst caller goes through useAsync; the
reasoning recorded in the code is not.

## 6. Why the live axis is BLOCKED BY TOOLING, not merely skipped
The defect's branch requires a 302 -> HTML response on an /api/ call. Three independent reasons a
live run cannot reach it here:
  a) The ticket itself records that this platform cannot produce the 302->HTML trigger naturally
     (established during VCST-5598); the original repro was fault-injected.
  b) Playwright MCP exposes NO route-interception tool — there is no browser_route. The only way to
     install a route handler is browser_run_code_unsafe, which hooks/enforce-real-user.mjs blocks,
     and the documented /* @allow-eval */ opt-in is scoped to "UI-FIX / DEBUG DOM experiment, NOT
     for test runs".
  c) The naturally reachable expiry (clearing the HttpOnly cookies) yields a 401 — a DIFFERENT
     branch, which this fix deliberately leaves unchanged. It can neither confirm nor refute the
     defect.
No browser agent was dispatched: it would have been structurally unable to reach the branch.
Evidence relied on instead: the unit RED->GREEN above (incl. the burst case), the deployed-bundle
markers, and the independent live sighting of the message during the VCST-5667 run.

To close the live axis properly, hooks/enforce-real-user.mjs would need its allowlist extended for
page.route / unrouteAll fault injection — the clean fix the hook's own guidance points at. This is
the third time in this session that gap has bounded a verification.
