vc-tools marketplace · vc-fix 0.8.3

The plugin a customer installs got more honest.

Four changes, all of which make the difference between a plugin we'd demo and a plugin we'd leave running on someone else's stack.

self-check Trustworthy by construction

Capture, judgement and surfacing are now three separate layers. The collector records every anomaly and is forbidden to decide whether it matters — so a signal the classifier doesn't recognise can no longer disappear before anyone analyses it.

deliver Contribution that contributes

Routes cut to issue or local. Previously a token with more rights delivered less — it printed a hand-off and sent nothing, while a weaker token filed automatically. A transient failure now retries once before falling back.

/project-init Writes where it should

Output root and plugin root are now separate concepts, so an installed plugin writes the project's profile and env into the project — never into its own versioned marketplace cache.

containment Guaranteed on both surfaces

The upstream report is a closed schema of enums and counts — zero free-text fields, so client code can't leak by type rather than by scrubbing. Plugin and in-repo mirror are byte-identical, CI-enforced.

vc-tools marketplace · New plugin

vc-perf — three instruments, because one is never enough.

Each layer answers a different question, and each is blind to something the next one sees. Picking the wrong one is how performance work produces confident nonsense.

L1 · BenchmarkDotNet

Did this code get slower?

Code-level A/B across two revisions, our override against the stock path, or an upstream before/after. Allocations and time, repeatable.

Blind toa round-trip you removed — it never left the process
L2 · k6 load harness

How does it hold up?

The live system under real concurrency — throughput, p95 latency, GC pressure, with optional counters captured alongside.

Blind towho is responsible for what it just measured
L3 · dotnet-trace

Who caused it?

Attribution: allocation churn, on-CPU time, and DB command shape, parsed back to the call sites that produced them.

Blind toanything the load didn't actually exercise
Reuses vc-fix wholesale — onboarding, repo routing, the backend developer and reviewer agents — and ships only the measurement delta. Advisory only, never a CI gate.

vc-tools marketplace · Live demo

What running it looks like.

One entry point routes to the right layer, then hands back a ranked list rather than a wall of trace output.

  • /perf-init — one-time: points the plugin at the local Aspire-hosted backend and the module's own benchmark targets.
  • /perf-loop — the diagnose entry point. Name an operation; it decides whether the question is L2, L3, or both, and runs them.
  • Ranked candidates — each one carries its evidence share, the shape of the fix, where the fix lands, and how to verify it. That's the artifact a developer picks up.
  • /perf-fix → /perf-verify — hand a candidate to the existing backend dev + reviewer agents, then re-measure to confirm the number actually moved.

vc-tools marketplace · Why it earns its place

The same discipline already found a real N+1.

From /qa-perf-measure, vc-perf's sibling for deployed environments — it counts dependency calls instead of timing them, because counts transfer across environments and latency does not.

  • Paired controls, same window — a positive and a negative control fire alongside the real measurement. That is what makes a null result mean "no change" instead of "dead instrument".
  • The fix worked; browsing was untouched — four identical searches collapsed to one, and catalog browsing did not move, because its redundancy is a different shape.
  • The residual scales — one Elasticsearch search per variation-bearing product on the page. Slope ≈ 1.0, and every measured value landed inside its independently predicted set across all ten cells.
  • The lever is batching — not deduplication. Filed as its own ticket with the measurement attached.

Agentic project · The pipeline

/qa-test decides twice before it does anything.

One ticket in, and the first step answers two separate questions — which flow this even is, and how much depth it deserves.

  • Axis 1 — the flow — by ticket type × status. A fix-ready Bug is a verification, not a feature test, so it runs RED→GREEN inline instead of going through authoring and promotion machinery it doesn't need.
  • Axis 2 — the path — FAST for a P2–P3 single-layer change; FULL for a Story, a P0–P1, anything cross-layer or revenue-critical.
  • The tie-break is written down — when in doubt, FULL. The cost of over-testing a small ticket is hours; the cost of under-testing a checkout change is a release.
  • Epic-aware — a story resolves its parent Epic and picks up integration coverage against Done siblings; --epic runs the children in series with a cross-story E2E and an Epic-level go/no-go.

Agentic project · What it's worth

What actually changed for whoever runs it.

Five things that used to cost a person time, a hand-off, or a judgement call they shouldn't have had to make.

BeforeEvery ticket got the same heavyweight treatment — a copy tweak cost what a checkout feature cost.
NowEffort tracks risk. FAST skips the BA-context and story-review agents, authors minimally, runs one execution agent, self-checks inline.
BeforeA fix-ready Bug was re-tested as though it were a new feature, authoring cases nobody needed.
NowA bug fix is a verification. Routed straight to RED→GREEN inline — the right job, at a fraction of the work.
BeforeNew cases landed in a run-scoped CSV and waited for a separate promotion pass to reach the real suites.
NowOne pipeline, one promoter. Cases go straight into the suites as Draft, are executed by the run that wrote them, and promote in-run only if green — non-promotable rows reverted.
BeforeA red run was a list of failures somebody had to interpret from scratch.
NowA red run is an action list. Step 5a triages its own FAILs through /qa-triage-results --fix — real bug vs test defect vs flake, with the taxonomy already defined.
BeforeTest → fix → re-test was three manual invocations with a deploy wedged in the middle.
Now--iterate closes the loop — bounded at 2 rounds, confirming every prerelease deploy. Merge and release stay human; the loop never touches them.

Agentic project · The new gates

Two kinds of gate, and the difference is the point.

One kind needs judgement, so we buy independence. The other needs none, so we make it deterministic and unarguable.

Judgement · three hard STOPs · FULL path

A fresh verifier, never the doer

  1. Step 3Artifacts reviewed & data seeded — before a single test runs.
  2. Step 5bTriage + AC/DoD vs implementation — with a quantified coverage estimate, before any verdict is filed.
  3. Step 5gPromotion sound — runs last and non-blocking, after the verdict and the close-out.
A fresh orchestrator instance re-derives the evidence from source — re-runs the lints, re-opens the artifacts, and delegates a live re-check on a different browser lane than the doer used. REJECT → reason + fix → re-verify once, then STOP.
Deterministic · no judgement required

Lints that simply refuse

  • ECLCitation gate — every edge-case reference in every suite must resolve.
  • IDsGlobally unique case IDs — hard-fails on a collision, across every CSV on disk.
  • CSVDeclared-but-missing suite — hard-fails, so a selection can never silently run zero cases.
  • TRIStamp staleness — flags assertions whose last audit has aged out.

Agentic project · Oracle review

Our oracles now prove themselves against reality.

/qa-review-oracles — one skill, two axes. The business-rules audit and the edge-case library shared their entire mechanism, so they became one thing with two entry points.

  • Three independent axes — documentation, live behaviour, and platform source, gathered per entry and compared.
  • Auto-apply on evidence, not approval — a confirmed correction is written straight to the oracle; contradictory or ungrounded ones become a proposal a human reads.
  • IDs are a citation contract — never renumber a surviving entry, never reuse a retired one. Renumbering silently repoints every correct citation, and no gate could detect it.
  • Parallel, but a single writer — fans out across up to three analysts each with their own browser lane, then applies serially. It never edits a test CSV; remaps go to the review skill.
The ECL axis had never had a gate at all. Its first run found 20 dangling references cited by ~65 cases across 7 suites — including one id that had never existed in any version of the library.

Where that leaves us

A plugin we can hand over, and a pipeline that spends effort where it matters.

Three things to take away:

The marketplace

Two products, not one

vc-fix is trustworthy enough to leave running on someone else's stack, and vc-perf gives performance work an instrument instead of an opinion.

The pipeline

Proportionate by default

Effort tracks risk, a bug fix is verified rather than re-tested, and new cases reach the real suites in the same run that wrote them.

The principle

Independent where it counts

Judgement gates buy a second opinion from someone who wasn't involved; everything else is deterministic. Merge and release stay human.
