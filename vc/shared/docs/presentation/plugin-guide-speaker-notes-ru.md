# Плагин vc-fix — заметки докладчика (RU)

Сопровождают презентацию [`plugin-guide.html`](plugin-guide.html) — «Setup & Feature Guide».
Порядок разделов совпадает с боковым меню гайда. Технические имена (команды `/…`, `vc-fix`,
`vc-qa`, MCP, PR, Jira/Azure Boards, GitHub/Azure Repos, Serena) произносим как есть.

**Аудитория:** смешанная — команда + руководство. **Длительность:** ~15–20 минут.
**Главная мысль, которую нужно донести:** мы перестали *просто пользоваться* QA-инструментом —
плагин теперь сам разворачивается, сам себя проверяет и сам поддерживает свои знания.

## 1. Что такое плагин (What the plugin is)

- `vc-fix` — это инструмент полного жизненного цикла бага для Virto Commerce: **завести баг →
  воспроизвести → исправить → выкатить → проверить**. Теперь ещё и **самодиагностика**.
- Ключевое: плагин **полностью автономен** — везёт с собой своих агентов, скиллы, команды,
  знания и конфиг. Ставится в любой проект и работает.
- Состав: **8 агентов, 16 скиллов, 8 команд** (`/project-init`, `/qa-bug`, `/qa-fix`,
  `/qa-verify-fix`, `/qa-monitoring`, `/qa-env-check`, `/vc-self-check`, `/vc-feedback`).
- **Почему важна настройка (сказать явно):** профиль, который пишется при онбординге, — это то,
  что позволяет `/qa-fix` направить каждый баг в **нужный репозиторий** (ваш кастомный код vs
  нативная платформа VirtoCommerce) и завести в **нужный трекер**. Без профиля — поведение
  по умолчанию: нативная платформа / Jira / GitHub.

## 2. Установка и настройка (Setup)

- Держим темп — это операционная часть, не нужно зачитывать каждую команду.
- Четыре шага: **(A)** добавить marketplace и поставить плагин → **(B)** `npm install` →
  **(C)** запустить мастер `/project-init` → **(D)** проверить.
- Акцент на **`/project-init`** — это «derive-driven» мастер: спрашивает только то, что реально
  влияет на конфиг (**имя окружения, трекер, код-хост, способ авторизации**), а всё остальное —
  клиент это или нативная платформа, организация, режим контрибуции, форк-аккаунт —
  **выводит сам** из токена и живого скана репозиториев.
- Он пишет `project-profile.json` + `.env.<env>` + `.env.local` + `.mcp.json` и печатает
  **таблицу готовности** (readiness table).
- Проверка: **`npm run env:check`** и **`/qa-env-check`** (быстро, <30 сек, только чтение).
- Про безопасность одной фразой: имена окружений произвольны, безопасность определяется
  `ENV_RISK`, а не именем — на `production` плагин по умолчанию **только для чтения**.
- Переход: «Что нужно рядом, кроме самого плагина — MCP-серверы.»

## 3. MCP-серверы и Serena

- **Обязательно** — Playwright (chrome / firefox / edge): автоматизация браузера для витрины
  и Admin SPA.
- **Опционально** (включают конкретные скиллы): `atlassian` → заведение багов, `github` →
  тестирование PR и маршрутизация, `postman`, `context7` + VirtoOZ → `/vc-docs`, Figma.
- **Serena** — общий сервер семантической навигации по коду (поиск символов, find-references,
  точечные правки). Включён в конфиге, но **ставится на каждой машине отдельно** (нужен
  `uv`/`uvx`). Агенты-разработчики используют его, чтобы находить и вносить правки быстрее, чем
  циклом «Grep → Read → Edit».
- Про секреты входа — одной фразой: пароли для входа лежат в отдельном минимальном файле
  `.env.playwright.local`, MCP подставляет их по имени и вырезает из логов; в контекст модели
  открытый пароль не попадает.

## 4. Как работать с плагином (Working with the plugin)

- Три сущности: **команда** (workflow, запускается сразу), **скилл** (методика + справочные
  файлы), **агент** (специалист, которому делегируют). На практике всё вызывается одинаково — слэшем.
- Два способа вызова:
  - **Явный слэш** — для всего, что имеет побочные эффекты (запуск тестов, заведение бага,
    правка кода). Это большинство инструментов, они защищены `disable-model-invocation`.
  - **Естественный язык** — только для read-only (`/qa-status`, `/qa-env-check`, `/vc-docs`).
- Показать **основную цепочку** (это и есть смысл плагина): 
  `/qa-bug` → `/qa-fix` → (человек ревьюит и мержит PR) → `/qa-deploy-pr` → `/qa-verify-fix`.
- Переход: «Теперь — то, что мы сделали нового в этом спринте.»

## 5. Самодиагностика (Self-diagnostics) — флагман

- **Главный тезис:** плагин теперь сам себя проверяет — «проверяет собственную домашнюю работу».
- Это **петля обратной связи «клиент → вендор»** (VCST-5509), три части:
  - **Коллектор** — пассивная телеметрия: фиксирует фазы/гейты каждого спана, ошибки инструментов,
    аномалии; помечает подозрительные спаны (`failed` / `degraded` / `silent_suspect`).
    Никогда не блокирует инструмент, не падает, вырезает секреты.
  - **`/vc-feedback` "…" 👍/👎** — ваш явный вердикт своими словами. Это **главный детектор
    ТИХИХ сбоев** — когда задача сделана неправильно, но *выглядела* нормально, и никакая
    эвристика этого не поймает.
  - **`/vc-self-check`** — диагноз: вердикт по каждому скиллу **OK / DEGRADED / BROKEN** + тяжесть +
    доказательство + гипотеза причины + конкретная предлагаемая правка (какой файл/строка).
- **`/vc-self-check deliver`** — доставка вычищенной контрибуции обратно в VirtoCommerce
  (PR / fork-PR / issue), под гейтом `feedback.mode`.
- **Обязательно подчеркнуть для руководства:** всё **opt-in и локально** (`selfDiagnostics: true`),
  наружу ничего не уходит без явного шага `deliver`, **код клиента не утекает**. Жизненный цикл:
  *записал → проанализировал → отдал → удалил*.
- (Если есть живой прогон — можно показать `/vc-self-check latest`.)

## 6. Маршрутизация для клиентских развёртываний — флагман (бизнес-ценность)

- **Тезис:** один плагин работает на любом развёртывании — на нашем внутреннем и на клиентском.
  Это и делает `vc-fix` **продуктом**, а не внутренним скриптом.
- Адаптеры: трекер — **Jira или Azure Boards**; хост — **GitHub или Azure Repos**. Баг заводится
  в трекер клиента в его родном формате.
- **Маршрутизация по владению (это данные, а не суждение):**
  - клиентский репозиторий → PR на **хосте клиента**;
  - баг платформы → **fork-PR наверх в VirtoCommerce**;
  - слишком сложный баг платформы → **GitHub Issue** наверх.
- **Жёсткий инвариант безопасности:** код клиента **никогда** не покидает проект клиента. Наверх
  уходит только код платформы + обезличенное воспроизведение, вычищенное от клиентских
  идентификаторов. Если баг воспроизводится только на клиентском коде — фикс **останавливается**.
- Красивый разворот для руководства: баг платформы, найденный у клиента, становится
  **контрибуцией наверх в продукт** — ценность возвращается в платформу.

## 7. /qa-deploy-pr — новая команда

- **Боль, которую убрали:** изменение часто рождает артефакты в нескольких репозиториях
  (модули + Platform + тема витрины). Раньше их приходилось вручную вписывать в манифест
  деплоя — это блокировало проверку. Теперь — одна команда.
- Что делает: собирает **все** свежие prerelease-артефакты по связанным PR тикета → перепинивает
  модули + Platform + тему **вместе в одном** изменении `vc-deploy-dev`.
- Безопасно по умолчанию: сначала dry-run diff; `--apply` открывает **один** gated deploy-PR;
  `--verify` проверяет, что всё встало живьём.
- Подчеркнуть: **никогда не мержит сам** — мержит человек, и это и есть деплой. После мержа
  разблокируются `/qa-test PR #N` и `/qa-verify-fix`.
- Фраза-итог: «Было — ручная многорепная рутина, тормозившая проверку. Стало — одна команда,
  один PR, проверено вживую.»

## 7а. Хотфикс-цепочка — новые команды (`/qa-bundle-check` → `/qa-hotfix` → `/qa-hotfix-check`)

- **Боль, которую убрали:** доставить уже смерженный фикс на замороженную стабильную линию — это была
  ручная рутина «cherry-pick + деплой» по бандлам и окружениям. Теперь это цепочка из трёх команд:
  **найти → выпустить → доставить**.
- **`/qa-bundle-check`** (найти) — наводит замороженный стабильный бандл на GitHub и подсвечивает
  каждый зафиксированный модуль / Platform / тему, у которого есть свежий патч **на той же линии**
  major.minor; никогда не новый minor (бандл должен отставать от master). Каждый хотфикс прослеживается
  до PR и связанной задачи трекера.
- **`/qa-hotfix`** (выпустить) — резолвит задачу → PR → фикс-коммит, проверяет, что он **MERGED и
  SHIPPED**, проходит гейт безопасности по форме фикса (один модуль, без bump-а версий зависимостей),
  затем по каждому бандлу создаёт ветку `support/<X.Y>` (если её нет) и делает cherry-pick, запуская
  workflow «Release hotfix». **Спрашивает, в какие бандлы** — набор latest-stable меняется со временем.
- **`/qa-hotfix-check`** (доставить + проверить) — поднимает версию модуля/Platform в манифесте деплоя
  для развёрнутых окружений `stable` + `regression`, ждёт зелёный деплой и подтверждение версии от
  `/api/platform/modules`, проверяет фикс вживую, комментирует и переводит задачу в Done, бампит
  latest-stable бандлы.
- Два принципа (те же, что и везде): **gated-записи, никогда не мержит сам** — по умолчанию dry-run /
  precheck, каждая запись под явным apply; **сомневаешься — STOP** (нет support-ветки, конфликт
  cherry-pick, фикс ещё не выпущен). `/qa-hotfix-check` — только доставка: если фикс не выпущен,
  отправляет обратно к `/qa-hotfix`.
- Фраза-итог: «Это та же наша тема — управляемая автоматизация: робот делает механику, человек мержит
  и принимает решение».

## 8. /qa-review-bl — новая команда

- Самое концептуально интересное. **База бизнес-правил** (`business-logic.md`) — это инварианты,
  против которых утверждают наши тесты. Раньше она устаревала, и чинить можно было только руками.
- Теперь команда **триангулирует** каждое правило по трём независимым источникам:
  **документация + живое поведение витрины + исходный код** — и **автоматически применяет**
  подтверждённые правки.
- Ключевое — **гейт по доказательствам, а не слепая автоматика**: подтверждённые (CONFIRMED /
  DRIFT / MISSING) применяются сразу; противоречивые / необоснованные — уходят в предложение
  на ревью человеку.
- Работает по требованию и **автоматически** как фаза жизненного цикла тестов — по тем правилам,
  которые затронул прогон. База знаний больше не гниёт тихо.
- Это наша повторяющаяся тема: **управляемая (gated) автоматизация**, а не слепая.

## 9. /qa-fix и команда разработчиков

- `/qa-fix VCST-XXXX` берёт уже заведённый баг и ведёт его по **лестнице гейтов G0–G7**,
  делегируя пишущей команде разработчиков по типу репозитория.
- Не зачитывать все гейты — назвать логику: **триаж → один репозиторий → воспроизвести (red) →
  минимальный фикс (green) → ревью → CI → E2E → ревью человеком**.
- Два принципа, которые обязательно проговорить:
  - **Никогда не мержит автоматически** (G7 — жёсткий стоп): заканчивается открытым PR.
  - **Сомневаешься — BAIL.** Чистая остановка — это успех, а не провал.
- Что заострили в спринте: маршрутизация встроенного Vue 3 sub-app модуля во фронтенд-команду
  (раньше был тупик), и **Serena** для быстрой символьной навигации — меньше и точнее диффы.

## 10. /vc-shell-fix — расширено и укреплено

- **Важная поправка (проговорить явно):** скилл чинит **любой** встроенный в модуль Vue 3 «shell»
  на `@vc-shell/framework`, а **не только page-builder** — page-builder был просто первым
  объявленным, это не предел.
- Два пути починки:
  - **логика/состояние** — доказывается red→green на **родном раннере** sub-app (`tsx --test`),
    без всяких заглушек (потому что `vue` — настоящий импортируемый пакет);
  - **DOM/шаблон** — эфемерный harness (vitest + `@vue/test-utils` + jsdom), который **вырезается
    из диффа перед PR**.
- Всё заземлено на реальный репозиторий: агент читает `package.json` sub-app (скрипты + пакетный
  менеджер) на месте, версии не хардкодятся. Автогенерируемый `src/api_client/` — не трогаем.

## 11. Дашборд регрессии и триаж (What it looks like)

- Здесь **показываем, а не рассказываем** — на слайде реальные прогоны этого спринта.
- **Живой пер-кейс дашборд:** статусы PASS / FAIL переключаются **вживую** по ходу прогона —
  не ждём конца сюиты. Гейт, плитки, «бублик» pass-rate обновляются на месте.
- **Трейс на каждый FAIL:** сетевые сбои с фрагментами тел + консольные ошибки с разобранным
  стеком, хранится рядом с прогоном (секреты вырезаны).
- **Кросс-ран overview:** тренд pass-rate по прогонам (столбики цветом по гейту) + фильтруемая
  таблица; текущий прогон помечается как живой.
- **`/qa-triage-results`** — классифицирует каждый провал: реальный баг продукта vs дефект теста
  (плохие шаги / плохая ассерция / устаревшие данные / устаревший тест) vs flaky / env. Красный
  прогон превращается в список действий. Тикеты сам не заводит — останавливается на человеке.
- (Показать оба скриншота: слева — один прогон, справа — overview.)

## 12. Планка качества (The quality bar) — слайд доверия для QA

- **Тезис:** каждая ассерция теперь обязана заслужить своё место.
- Два структурных изменения:
  - **Provenance-гейт ассерций** — каждая сгенерированная ассерция помечена источником (спека /
    бизнес-правило / документация / живое наблюдение). Необоснованные **блокируются** от промоушена;
    новая фича должна быть заземлена вживую, прежде чем попасть в сюиту.
  - **Данные, независимые от окружения** — у каждого окружения свои алиасы, никаких runtime-ID
    в закоммиченных файлах: сюита не может случайно зарезолвить данные другого окружения.
- Плюс: доступность **WCAG 2.2 AA** (`/qa-accessibility`, axe-core) и test-data-инженер,
  который теперь **и пишет сидеры, и прогоняет их вживую** с drift-guard проверкой.

## Закрытие (30–45 сек)

Три вещи, которыми стоит гордиться:
1. **Плагину можно доверить клиента** — поддержка клиентских развёртываний + жёсткий инвариант
   неутечки клиентского кода.
2. **Он сообщает, когда ошибся** — самодиагностика + `/vc-feedback` + живые трейсы + самопроверяемая
   база знаний закрывают петлю, которую старый подход закрыть не мог.
3. **Люди ревьюят — машины пашут** — деплой, фикс, хотфикс, поддержка знаний автоматизированы до
   последнего безопасного шага, а дальше — человек. **Никогда не мержим автоматически.**

Дальше — вопросы и живое демо (`/vc-self-check` или `/qa-deploy-pr --dry-run`).
