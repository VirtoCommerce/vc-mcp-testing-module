Agentic QA · vc-fix

Setting up the plugin, and what each new feature actually does.

Two parts: how to install and drive the vc-fix plugin, then a detailed walk through each capability we shipped this sprint — what it is, how you invoke it, and how it works under the hood.

What the plugin is

A bug-lifecycle toolkit for Virto Commerce, distributed as a Claude Code marketplace plugin. It files, reproduces, fixes, deploys, and verifies bugs against a live deployment — and it now diagnoses its own runs.

The plugin is fully self-contained — its own agents, skills, commands, knowledge, and config — so it works wherever Claude Code installs it. It currently ships 8 agents, 16 skills, and 8 commands: /project-init (onboarding), /qa-bug, /qa-fix (+ a write-capable developer team), /qa-verify-fix, /qa-monitoring, /qa-env-check, and the self-diagnostics pair /vc-self-check + /vc-feedback.

The point of setup: the profile you write during onboarding is what lets /qa-fix route each bug to the right repo (your custom code vs the native VirtoCommerce platform) and file it to the right tracker (Jira or Azure Boards). Without it, everything defaults to the native-platform / Jira / GitHub behavior.

Setup — install & configure

Roughly 5–15 minutes per environment. Prerequisites: Claude Code ≥ 1.0, Node ≥ 18, a storefront URL, an Admin/platform URL, and one storefront + one admin test account.

  1. Add the marketplace & install the plugin

    In Claude Code, add the marketplace and install. Claude clones the plugin into its cache and auto-discovers the agents, skills, commands, and MCP config.

    /plugin marketplace add VirtoCommerce/vc-mcp-testing-module
/plugin install vc-fix@vc-tools
  2. Install dependencies

    From the plugin install directory (Claude Code prints the path after install), pull the Node dependencies the scripts and orchestrators need.

    npm install
  3. Run the onboarding wizard — /project-init

    The derive-driven wizard asks only what genuinely shapes config — the environment name, the bug tracker (Jira / Azure Boards), the code host (GitHub / Azure Repos), and an auth preference per axis (a PAT is recommended; otherwise browser / CLI login — never passwords). It derives the rest — native-platform vs client project, your org, contribution mode, fork account — from the token plus a live module/repo scan.

    It writes project-profile.json + .env.<env> + .env.local + .mcp.json, then prints a readiness table confirming access.

  4. Verify

    Confirm the install and env load, then run a fast read-only environment check.

    npm run env:check         # env vars present & valid
/qa-env-check             # both surfaces + MCP servers, <30s

Environments & safety

Env names are arbitrary strings (dev, qa, staging, prod, client_eu…). Safety is gated by ENV_RISK, not by the name — on production the plugin is read-only by default and admin-write actions refuse to run without an explicit escape hatch.

BucketFileCommittableHolds
Plugin defaults.env.defaultsYesSandbox cards, public URLs — same for everyone.
Per-env config.env.<env>Yes (your fork)FRONT_URL, BACK_URL, ENV_RISK, MODULES_ENABLED, tracker key.
Secrets.env.localNo (gitignored)Passwords, API tokens. Per-env via suffix (USER_PASSWORD_QA…).

Re-running after an upgrade? /project-init --check migrates a stale project-profile.json to the current schema — no full re-onboarding (see Client-deployment routing).

MCP servers & Serena

Browser automation is required; the rest gate specific skills.

  • Required — Playwright (chrome / firefox / edge): browser automation for storefront + Admin SPA + cross-browser. Configured in .mcp.json.
  • Optional, skill-gating: atlassian → /qa-bug filing; github → PR testing & routing; postman → API skills; context7 + VirtoOZ → /vc-docs; figma-remote-mcp → design comparison.

Serena is the shared semantic code-navigation server (LSP-backed symbol search / find-references / precise edits). It's enabled in tracked config but installed per machine — needs uv/uvx on PATH. The developer agents use it to find and apply fixes faster than a Grep → Read → Edit loop.

/plugin marketplace add anthropics/claude-plugins-official
/plugin install serena@claude-plugins-official
# then restart Claude Code — verify: claude mcp list → plugin:serena … ✔ Connected
Login secrets for browser tests go in a dedicated, minimal .env.playwright.local pointed at by the Playwright --secrets flag — never .env.local (which also holds API tokens). The MCP substitutes the value by NAME and redacts it from logs, so plaintext never enters the transcript.

Working with the plugin

Three kinds of thing, one way to invoke them.

KindWhat it isYou…
CommandA testing workflow that runs now — the plugin's verbs.Type the slash: /qa-bug, /qa-fix.
SkillA packaged methodology + reference files. Some run work, some just inform.Invoke like a command; some auto-pull when relevant.
AgentA specialist Claude delegates to for multi-step work.Rarely called directly — commands dispatch them for you.

How to invoke

  • Type the slash explicitly for anything with side effects — a test run, a bug filing, a code change. That's the majority of the toolkit, guarded by disable-model-invocation so Claude never kicks one off on its own.
  • Natural language works only for the read-only few (/qa-status, /qa-env-check, /vc-docs). "Show me the QA dashboard" runs /qa-status; "run the smoke suite" will not — you type it.

Reading argument hints

Every command advertises its arguments in the / menu. [a|b|c] = pick one; VCST-XXXX = a ticket id; PR #NNN = a pull request; <description> = free text; no argument = the default/interactive mode.

The core chain

The tools hand off to each other. The bug lifecycle is the one you'll run most:

/qa-bug "cart total wrong on B2B order"   # reproduce + file the ticket
/qa-fix VCST-1234                        # triage → fix → open a PR (never merges)
# …a human reviews & merges the PR…
/qa-deploy-pr VCST-1234 --apply           # deploy the artifacts to the test env
/qa-verify-fix VCST-1234                   # confirm the fix live, close the loop

Self-diagnostics

Flagship · client→vendor feedback loop (VCST-5509)

The plugin observes whether its own skills ran correctly — and lets you say so

A feedback loop so a customer-installed plugin can tell whether its own commands, skills, and agents did the right thing, and — opt-in — report quality issues back to VirtoCommerce, without ever mutating the client install or leaking client code. Three moving parts:

Collector
Passive telemetry — a hook records each skill/command span's phases, gates, tool errors, denied permissions, and an anomaly score to a local, gitignored trace, and flags spans that look failed / degraded / silently-suspect. It never throws, never blocks a tool, and redacts secrets.
Your verdict
/vc-feedback "<what happened>" 👍/👎 — you tell the plugin, in your own words, whether it just did the right thing. This is the main detector of SILENT failures — a task done wrong that looked fine and no heuristic can catch. The UserPromptSubmit hook attaches the verdict to the open span; the model just acknowledges — nothing is sent.
Diagnosis
/vc-self-check — reads the trace + transcript against an expectations oracle (expected phases/gates + an S0–S3 severity rubric) and writes a local DIAG-*.md: a per-skill verdict of OK / DEGRADED / BROKEN with evidence, a root-cause hypothesis, and a concrete proposed fix (which file/line). It diagnoses the flagged spans + any /vc-feedback verdicts.
Delivery
/vc-self-check deliver — turns a confirmed finding into a scrubbed contribution (PR / fork-PR / issue, routed by your GitHub-token rights), gated by the profile's feedback.mode. --batch consolidates all local DIAGs into one deduped report; --confirm files it; --purge cleans up. Client source is stripped before anything leaves.

Opt-in, local, ephemeral. Nothing is recorded unless selfDiagnostics: true is present in your profile — absent or false, the hook is a full no-op and no .vc-fix/ folder is created. Nothing leaves your machine except through the explicit, feedback.mode-gated deliver step. The lifecycle is log → analyze → contribute → delete: once a finding is upstream, the processed session's local artifacts are removed.

Client-deployment routing

Flagship · onboarding + /qa-fix

One plugin runs on any deployment — ours or a customer's

Tracker and code-host adapters plus ownership-aware routing let the same plugin file bugs and open fixes correctly whether it's running on VirtoCommerce-internal infra or a customer's stack — behind a hard security invariant.

Where a fix is delivered (routing is data, not judgment)

Routed repoOutcomeDelivery
Client repo (custom module / theme / storefront fork)fixable → PRPR on the client's host — GitHub or Azure Repos.
Platform repo, operator = VirtoCommercefixable → PRDirect PR to VirtoCommerce/<repo>.
Platform repo, operator = clientfixable → PRFork-PR upstream to VirtoCommerce, from the client's fork.
Platform repo, too complex / multi-reponot fixable → issueA GitHub Issue on the upstream (client deployments only).
Client-code containment — a hard invariant. Client code MUST NEVER leave the client's own project. The upstream receives contribution only — platform-authored fixes + platform-generic reproduction, scrubbed of client source, paths, identifiers, and secrets. If a bug reproduces only with client code, it is not upstream-contributable → the fix STOPS and hands back to the client team. Enforced at routing, at code review, and in the developer team.
Trackers
Jira or Azure Boards — bugs file in the tracker's native shape (Azure work items match the lean gold-standard form: abstract summary → repro, metadata in dedicated fields, auto-assigned to the current sprint).
Hosts
GitHub or Azure Repos, with PAT or browser/CLI-login auth per axis.
Upgrades
/project-init --check reconciles a stale profile to the current schema — adds new fields with safe defaults, prunes obsolete ones, and asks you about anything that's a real decision.

/qa-deploy-pr

New command

Deploy all of a change's fresh artifacts together, in one manifest update

A change often spreads prerelease artifacts across several repos — one or more modules, the Platform, the vc-frontend theme. Pinning them into the deploy manifest by hand blocked PR-testing and fix-verification. This gathers them all and deploys them together.

Invoke
/qa-deploy-pr <ticket-key> [--pr owner/repo#N] [--module Id=Ver] [--platform Ver] [--theme url] [--env <name>] [--apply] [--verify]
Resolve
Reads the tracker ticket's linked PRs across all repos (or your explicit --module/--platform/--theme/--pr set) → picks each PR's latest vc3prerelease CI build.
Repin
A minimal-diff update of backend/packages.json (AzureBlob / BlobName + PlatformVersion) and theme/artifact.json — all targets in ONE vc-deploy-dev change, on the branch that maps to your TEST_ENV.
Apply
Dry-run combined diff by default. --apply opens ONE gated deploy PR — a direct same-repo push if your account has write, otherwise a fork PR (it prints the web-edit URL on a 403).
Verify
--verify reports per-target deploy state — the env-branch pin plus the live /api/platform/modules version.
Never merges. It ends at an open PR for a human to merge — merging is what actually deploys. Once merged, /qa-test PR #N and /qa-verify-fix can finally run against the change.

Hotfix lifecycle

New commands · a 3-step chain

Backport a released fix to a frozen stable line — end to end

Getting a merged fix onto a frozen stable bundle used to be a manual cherry-pick-and-deploy chore across bundles and environments. Three commands now chain it: discover what's missing → release it onto the support line → deliver it to the deployed environments and verify.

Discover
/qa-bundle-check vN | <package.json-url> — points a frozen stable bundle at GitHub and flags every pinned module / Platform / Theme that has a newer same-line patch waiting; never a newer minor (a frozen bundle is meant to trail master). Each hotfix traces to the PR that raised the version and its linked tracker task.
Release
/qa-hotfix VCST-XXXX [bundles] — resolves the task → its linked PR → the fix commit, confirms it is MERGED and SHIPPED, checks a fix-shape safety gate (single module, no dependency-version bump), then per bundle creates the support/<X.Y> branch if missing and cherry-picks onto it, triggering the repo's "Release hotfix" workflow. It ASKs which bundles — the latest-stable set changes over time.
Deliver + verify
/qa-hotfix-check VCST-XXXX — bumps the module/Platform version in the deploy manifest for the deployed stable + regression envs, waits for the deploy Action to go green and /api/platform/modules to report the new version, verifies the fix live, comments on and transitions the tracker task to Done, and bumps the latest-stable bundles.
Gated writes, never auto-merges. Every command is read-only by default (a dry-run / precheck); each write is gated behind an explicit apply. They STOP cleanly at any wall — no support branch, a cherry-pick conflict, or a fix that hasn't shipped yet — and hand back to a human. /qa-hotfix-check is delivery-only: if the fix isn't released yet, it points you back to /qa-hotfix.

/qa-review-bl

New command

Our business-logic knowledge base audits and corrects itself

The business-logic oracle (business-logic.md) is the set of testable invariants our tests assert against — and it used to drift, fixable only by hand. This triangulates each rule against three independent sources and applies confirmed corrections automatically, gated by evidence rather than blind trust.

Invoke
/qa-review-bl all | domain <name> | BL-<ID> | diff [--dry-run]
Triangulate
Each BL-* invariant is checked against docs (VirtoOZ), live behavior (Playwright), and source code (GitHub MCP) — three axes, per rule.
VerdictWhat it meansAction
CONFIRMEDAll sources agree with the current rule.No change.
DRIFTSources moved; the rule is stale.Auto-applied to the oracle (body-only, stamped, env-agnostic).
MISSINGA real invariant not yet recorded.Auto-added.
CONTRADICTORY / UNGROUNDED / RETIRESources disagree, or evidence is thin.Routed to a human-review proposal — never auto-applied.

It runs on demand, and also automatically as a phase of the test lifecycle — scoped to just the rules a run touches — so the knowledge base can't quietly rot. Every run leaves an audit trail. This deliberately supersedes the former "never auto-edit business-logic.md" rule — the 3-source evidence bar is what replaces human approval for the confirmed cases.

/qa-fix & the developer team

Matured this sprint

Autonomous fix of a filed bug — automated to the last safe step

/qa-fix VCST-XXXX takes a bug already filed by /qa-bug and walks it through a gate ladder, delegating to a write-capable developer team by repo kind. It never auto-merges — it ends at an open PR for human review.

GateWhat must pass
G0 TriageA simple, low-risk, code-fixable defect — clear repro, localized cause, no refactor, no breaking change. When in doubt, it BAILs (a clean STOP is a success).
G1 Single repoResolves to exactly one allowed repo; ownership + contribution plan pick the PR target (see routing).
G2 Reproduce (red)A new unit test encodes the bug and fails on current code.
G3 Fix (green)A minimal diff turns it green; all pre-existing tests stay green and unmodified; invariants preserved.
G4 ReviewA kind-appropriate reviewer agent checks single-repo scope, no test edits, idiomatic & minimal, no breaking contract.
G5 Build + CILocal build/tests, then the PR's CI — build, unit tests, SonarCloud quality gate, and the deployed auto-tests — all green.
G6 E2E verifyOnce the artifact deploys, a QA expert reruns the affected regression live.
G7 Human reviewHard stop — never auto-merge. Ends at an open PR; a human merges.

Sharpened this sprint

  • Module sub-app routing — a bug in a module's embedded Vue 3 shell now routes to the frontend dev team (was previously a dead end), reproduced with the sub-app's own runner and fixed in a scoped single-repo PR.
  • Serena symbol navigation — the fix step uses Serena for fast, precise symbol-level navigation and editing across a polyglot module, yielding smaller, more surgical diffs.

/vc-shell-fix

Broadened + hardened

Fix any module's embedded @vc-shell app — not just page-builder

The skill fixes a vc-module-* repo's embedded Vue 3 "shell" sub-app built on @vc-shell/framework. Page-builder was only the first one declared — it is not the limit. Any sub-app registered in the routing config is in scope, and the sub-app ships inside the module repo, so it stays a single-repo fix (owned by the frontend dev team, since it's a different stack from the module's C#/AngularJS Admin UI).

Path 1 — state/logic
A composable / store / service bug is proven red→green with the sub-app's own real tsx --test runner and plain Vue reactivity — no stubbing, because vue is a real importable package.
Path 2 — DOM/template
A mounted-component / rendering / slot / CSS bug uses an ephemeral vitest + @vue/test-utils + jsdom harness that reuses the sub-app's own vite.config.ts — stripped from the diff before the PR.

Grounded, not assumed: the fix agent reads the sub-app's own package.json (scripts + package manager) and any first-party .claude docs at fix time, so it works against the actual repo — versions and package managers are never hardcoded. The auto-generated src/api_client/ is off-limits (an anchor there is an upstream root cause, not a shell fix).

Regression dashboard & triage

Matured this sprint

See failures as they happen, then find out why

The regression pipeline gained live visibility and a triage step that turns a red run into an action list.

  • Live per-case dashboard — a self-refreshing HTML report where each case flips PASS / FAIL / BLOCKED live as the run proceeds; you no longer wait for a whole suite to finish. Gate verdict, summary tiles, and a pass-rate donut update in place.
  • Per-failure trace — every real FAIL writes an isolated trace file (network failures with body snippets, console errors with parsed stack frames), kept with the run and linked from the dashboard. Secrets are redacted before writing.
  • Cross-run overview — a consolidated dashboard trends pass-rate per run (bars coloured by gate) with a filterable table of every run in the window; the in-progress run flags live.
  • /qa-triage-results — classifies each failure as a real product bug vs a test defect (bad steps / bad assertion / stale data / stale test) vs flake / env / known, verifies the real ones live, and routes test-defect fixes automatically. It never files a ticket and never auto-fixes — it stops for a human.

The quality bar

Raised this sprint

Every assertion has to earn its place

Trustworthy tests come from grounded assertions and honest data — both were made structural, not conventions.

  • Assertion provenance gate — every generated assertion is tagged with its source: a spec, a business rule, docs, or a live observation. Ungrounded assertions are blocked from promotion, and a genuinely new feature must be grounded live before it ships into a suite.
  • WCAG 2.2 AA accessibility — /qa-accessibility was sharpened for WCAG 2.2, its axe-core source bumped, and the read-only scan allow-listed so it runs cleanly as a safe interaction. A real widget audit was filed this sprint.
  • Env-agnostic test data — every environment owns its own data aliases and no runtime IDs live in committed files, so a suite can never resolve another environment's data by accident. New RBAC fixtures keep coverage current against the live product.
  • Test-data engineer, end to end — the agent now authors seeders and runs them live against a non-prod environment with drift-guard validation, rather than only writing the code.
