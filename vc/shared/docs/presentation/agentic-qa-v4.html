Flagship Command · Tiered Lifecycle

/qa-test — Effort Tracks Risk, and Nobody Grades Their Own Homework

Testing a P3 config tweak like a P0 cross-layer feature wastes a day; testing a P0 feature like a tweak ships a bug. So /qa-test routes on two axes before it does any work — and at the gates that matter, the evidence is re-derived by someone other than the agent that produced it.
Axis 1 — FLOW, by ticket type × status
Bug, fix-ready→ runs /qa-verify-fix RED→GREEN inline
Bug, hotfix status→ /qa-hotfix-check
Sub-task→ inherits its parent's type
Story / Task / Epic→ feature-test
Single source of truth: knowledge/execution/ticket-routing.md — tracker-agnostic, shared by five commands.
Axis 2 — PATH, within feature-test

FAST

P2–P3 · single layer · single domain. Skips the BA-context and story-review agents, minimal authoring, one execution agent, inline self-checks, no exploratory.

FULL

Story · P0–P1 · cross-layer · ≥2 domains · critical-revenue · unclear surface. Concurrent BA + story review, full authoring, independent verifiers.
When in doubt → FULL.
🔍 The independent verifier — three hard-STOP gates, FULL path only
Step 3
Artifacts reviewed + data seeded
→
Step 5b
Triage + AC/DoD vs implementation, with a quantified coverage estimate
→
Step 5g
Promotion sound (runs last, non-blocking)
A fresh qa-lead-orchestrator — never the pipeline's own orchestrator, never the step's doer. It re-derives evidence from source (re-runs the lint/validate/metrics gates, re-opens the evidence, delegates a live re-check on a different browser lane) and returns APPROVE / REJECT. On REJECT: reason + fix → the doer fixes → re-verify once, then STOP.
New cases go live in-run
Step 3 appends them straight into regression/suites/ as Draft — the runner does not skip Draft, so Step 4 actually executes them. Step 5g then flips the green ones Draft → Automated and reverts the rest.
--iterate — bounded fix loop
A FAIL auto-runs /qa-fix → /qa-deploy-pr deploys the prerelease → re-test, up to 2 rounds, then STOP. It always re-tests an unmerged build, so the never-auto-merge guard is never touched.
--epic — stories in series
Dependency-ordered, seeded exit state carried story → story, a final cross-story E2E, and a roll-up of the per-story release gates into one Epic-level GO/NO-GO.
The human stays terminal. /qa-test ends at a ratified Feature Release Gate with a GO/NO-GO recommendation — it never marks the ticket done, and merge and release are always a person's call.

/qa-deploy-pr Unblocks /qa-test PR #N
Gathers every fresh CI prerelease artifact a change produced — modules + Platform + vc-frontend theme — and deploys them together, in ONE vc-deploy-dev manifest update.

🔗 The Hotfix Chain — three commands, in order
/qa-bundle-check
Discover. Which pinned module / Platform / Theme versions in a frozen stable bundle have a newer patch on the same major.minor line? Never flags a newer minor — a bundle is meant to trail master. Each hit traced to its PR + tracker task.

/qa-hotfix
Release. Task → linked PR → fix commit; verify MERGED + SHIPPED, then per bundle cherry-pick onto support/<X.Y> and trigger the repo's "Release hotfix" workflow. STOPs when no support branch exists.

New · Self-Maintenance

The Suites and Oracles Now Audit Themselves

A 4,155-case corpus rots silently. The old lint could prove an assertion carried a provenance tag — never that the tag was still true. A {DOC} whose doc changed and an {OBSERVED} from a six-month-old build both linted green. Three mechanisms close that.
/qa-triage-results
A run tells you which tests failed. This works out why, and what to do.
  • Collects every non-passing case with its trace, screenshots, console, network, CSV row + a cross-run flaky flag
  • Classifies: real product bug vs test defect (bad steps / bad assertion / stale data / stale test) vs flaky / env / known
  • Ambiguous → REAL_BUG/LOW, never relabelled as a test defect
  • --fix routes test defects to /qa-review-tests --fix and drafts the real bugs
  • Never files a ticket · never triggers /qa-fix
Dimension 11 — triangulation
Dim 10 checks a provenance tag exists. Dim 11 checks it is true.
  • Every assertion triangulated against docs + live + source
  • Verdicts: CONFIRMED · DRIFT · MISSING · CONTRADICTORY · UNGROUNDED · RETIRE
  • Auto-applies only CONFIRMED (refresh the Audited: stamp) and DRIFT (rewrite the drifted assertion) — the other four are proposals; deprecation stays human
  • The stamp is the rotation state — it lives in the row it describes, so there is no ledger to desync
/qa-review-oracles
The same mechanism applied to the two shared oracles — merged into one skill, two axes.
  • bl → business-logic.md · gate bl:lint · column Business_Rule

/qa-fix — From Filed Bug to Open PR, Autonomously

Picks up an already-filed JIRA bug and walks an 8-gate ladder (G0→G7). Passes a gate or STOPS. The cheap, code-free gates fire before any clone — rejected tickets cost almost nothing.

Simple · low-risk · localized · no refactor · no breaking change · BL-* preserved. When in doubt, BAIL.

G4 Code Review

the kind-routed reviewer gates the diff: single-repo · no edited tests · minimal & idiomatic

G1 Single Target Repo

Exactly one allowed repo — vc-module-* / vc-platform / vc-frontend or a client-owned repo. Never guess: multi-repo → STOP

G5 Build + CI + SonarCloud

Build · unit tests · GitHub Actions green · SonarCloud quality gate must be green

G2 Reproduce (Red)

New unit test encodes the STR and fails on current code (xUnit / vitest)

G6 E2E / Deploy Verify

Post-deploy /qa-regression by qa-backend-expert (backend is static-only in CI)

G3 Fix Correctness (Green)

Minimal diff turns repro green; all pre-existing tests stay green & unmodified

G7 Human Review — Hard Stop

NEVER auto-merges. Ends at an open PR awaiting a human

🛡️ Triple no-auto-merge guard: harness deny-list · orchestrator never calls merge · agents forbidden gh pr merge. Interactive opens a normal PR; CI opens a --draft.
STOP / BAIL is a success. Anything ambiguous, complex, breaking, cross-repo, or low-confidence leaves the ticket for a human — a wrong GO erodes trust. Twin of headless ci/run-fix-cycle.ts.
🧭 Ownership routing is data, not judgment. project-profile.json (written by /project-init) decides where the result is delivered: a client repo → PR on the client's own host (GitHub or Azure Repos); a platform repo → a direct PR, or a fork-PR when the operator is the client. G2–G6 are identical either way.
🔒 Client-code containment — a hard invariant. Client code never leaves the client's project: a client repo is never forked, PR'd, or issue-filed upstream, and an upstream contribution carries platform code only. Ownership uncertain ⇒ treat as client and STOP. When containment conflicts with "fix the bug", the fix stops.

New · Performance

Measuring Performance Without Fooling Yourself

Shared test environments are noisy: latency swings with whatever else is running, so a p95 that improved after a change proves nothing. The governing rule — counts transfer across environments; latency does not. So we count work, not milliseconds.
/qa-perf-measure
Measures backend work per request on a deployed environment and proves whether a change actually moved it — by joining App Insights requests ⋈ dependencies on operation_Id and counting dependency calls by type.

Why a null result is trustworthy here: every run carries paired positive and negative controls in the same window. Without them, "no change detected" is indistinguishable from "the instrument was pointed at the wrong thing" — which is exactly how a measurement quietly lies.
Measure-and-report only — it never files a tracker item, transitions one, or opens a PR. Recipe + the four known confounds: knowledge/execution/es-call-ab-method.md.

L1 · BenchmarkDotNet
Code-level A/B on allocations and time. Blind to removed round-trips — which is why L1 alone can't answer an N+1 question.
L2 · k6 + dotnet-counters
How the running system behaves under load — throughput, p95, GC pressure.
L3 · dotnet-trace

New · Self-Diagnostics

The Plugin Watches Itself — and Can't Grade Its Own Silence

Once the system ships to other people, its worst failure mode isn't a crash — it's a skill that quietly does the wrong thing and reports success. So the plugin records its own behaviour, judges it separately, and only then decides whether to bother you.
Tier A Passive collector opt-in, default off
A hook on SessionStart / UserPromptSubmit / PostToolUse[Skill] / SubagentStop / Stop reads the transcript delta at each skill boundary and records outcome-classified signals — tool errors, denied permissions, hook failures, stderr on an exit-0 tool, self-labelled degradation prose — into a local, gitignored .jsonl.
Secrets are redacted. It never throws and never blocks.
Tier B /vc-self-check on demand
A self-check-diagnostician subagent reads that telemetry, the transcript, and an oracle of what each skill was supposed to do, and returns a validated finding struct: per-finding OK / DEGRADED / BROKEN + severity S0–S3 + evidence + root cause + a proposed fix.
Writes no report file — the oracle and raw telemetry never enter the main conversation.
The design lesson — capture, judgement and surfacing are three layers
Originally one test at capture time decided all three at once, so any signal the classifier didn't recognise ceased to exist. A real onboarding run printed a WARN in its own readiness table and then self-diagnosed "no plugin issues detected" — 31 successful spans, nothing flagged. Now the collector records that something happened and is forbidden from deciding whether it matters; every anomaly becomes a durable observation with no verdict field. Two invariants make the old failure unrepresentable: a run may only call itself clean when there are zero observations and zero flags, and any self-reported warning forces at least "needs attention".
🔒 Containment by type, not by denylist
The outbound artifact is built from a closed schema — every field is a fixed-vocabulary enum or a number, zero free-text. Repo, module and org names never travel; error text is classified locally and only the code is sent. A client-data leak is impossible by type.
🗑 Ephemeral by design
The lifecycle is log → analyze → contribute → delete. On a successful, consent-gated GitHub Issue the session's own artifacts are removed — the issue is now the source of truth. A tombstone stays so a rebuilt session can't re-nag.
👍👎 /vc-feedback
An explicit verdict on the current session — the highest-value signal we get, because it's the main way a silent failure gets caught. Recorded locally; upstream it travels as a count only, never as prose.
