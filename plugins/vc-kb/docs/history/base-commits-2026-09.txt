90d6630 2026-09-10 Derive the id from the subject; drop the counter and the id map
Two people's agents writing this base have no shared counter to hand out the next
number, so a sequence is wrong the moment there is more than one writer. A
timestamp does not fix that -- it makes it worse. Two agents recording the SAME
fact would mint two different ids and the base would hold the fact twice, which is
the drift this project keeps paying for. A knowledge base wants two independent
captures of one fact to COLLIDE, not to avoid each other.

So the id is sha256(subject) truncated to 8 uppercase hex digits:

  * same subject, same id, on any machine, in any order, with no shared state
  * nothing to merge -- derived-ids.json is deleted, and with it a file that
    duplicated the id/subject mapping catalog.md already carries
  * the id is checkable: `kb validate` recomputes it from the subject, so a
    hand-edited id or a renamed subject is caught rather than dangling later
  * a genuine hash collision is a hard error at extract time, never a silent
    merge of two facts

Also: brain.json is now kb.json, and the word is gone from the code and the docs.
