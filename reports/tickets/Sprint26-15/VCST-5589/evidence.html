The defect and the fix

The three Sales Rep statistics operations — salesRepCustomerOrderStatistics, salesRepCustomerCartStatistics, salesRepCustomerCounts — inherited the Apollo client's default cache-first policy. Their variables are deliberately day-stable: buildStatisticsWindows rounds every upper bound to the end of the UTC day so the backend's own statistics cache engages. Identical variables plus cache-first means every remount is a pure cache hit, so nothing short of a full page reload — which discards the cache entirely — ever refetched.

The fix adds one shared constant and passes it to all three useQuery calls. Nothing else changed; 5 files, +186/−5, of which +167 is a new spec file.

The decisive observable

Under cache-first, a request whose variables are byte-identical to one already in the cache cannot reach the network. So the proof is not merely "a request fired" — it is a request fired despite byte-identical variables, and came back with a different answer.

F1 — the contradiction survives, with its polarity inverted

Medium · in blast radius · recommend a follow-up ticket

The ticket's goal was that a widget should stop contradicting the list on the same screen. After the status change and an SPA navigation cycle, the KPI now reads New orders 0 / $0.00 — correct — while the Recent orders table directly beneath it still shows that order as "New en1". salesRepOrders was not in the fix's scope and remains cache-first; the network trace confirms only requests 245/246/247 fired, with no SalesRepOrders among them.

This is not a failure of VCST-5589 — the ticket scoped exactly three operations and all three are correct — and not the acknowledged out-of-scope "already on screen" case, since this is a genuine remount. It is the residual half of the symptom, and it does contradict the ticket's acceptance criterion "values match the corresponding lists/details without a page reload". The fix is one line per op: extend STATISTICS_FETCH_POLICY to the sibling list operations.

Re-verification with richer data

The first pass ran against a seed of 1 order, 0 carts and 1 product, which left several assertions unevaluable and one finding confounded: BL-SR-003 makes a null *ChangePercent correct when the previous-period baseline is 0 — exactly our data — so "the UI doesn't render a change indicator" may have been unfair. Data was seeded (9 orders / $1,937.00, 2 active carts, 5 ranked products, a second served org) and every case re-run, cross-checked this time against the UI's own live GraphQL request documents — what it asks for versus what it renders.

Two honest corrections to the plan behind this pass. The intended discriminator — a real +100% week-over-week on the carts tile — could not reach the UI: the cart query does not select comparison at all, and the UI's own prevWeek window is a single day (Jul 27, matching elapsed week-to-date since Aug 3 is a Monday) while the prior cart is dated Jul 28. The order tiles settled the question instead. And createdDate on an order proved server-assigned and unwritable, so no previous-week / previous-month / last-year baseline can be seeded at all — a permanent constraint on this class of assertion, not a gap in this run.

Other findings

  • F2 — Info, re-scoped. The dashboard tiles discard data the API returns: no AOV, and no period-over-period $/% even though a non-null signed totalChange is fetched. SalesRepCustomerCounts likewise never selects comparison, so the month-over-month indicator SR-HD-007 expects cannot render by construction. On the profile, the MTD tile shows a share-of-YTD ratio (79%, arithmetically correct) rather than a period-over-period change, and shows neither count nor MTD AOV. Either the UI should render these, or the {SPEC} assertions in SR-HD-004/005/007 and SR-CP-028/030 should be corrected to the implemented design. Graceful degradation holds throughout — no NaN, Infinity, or raw null anywhere.
  • F2b — Info, unresolved. No loading indication was observable during the in-flight window across 5 attempts including a cold load. Two causes cannot be separated with real-user tooling: the round trip finishes inside a tool tick, and an overlay carrying no role/aria-busy would be invisible to the a11y tree regardless. The ticket's expected result #4 stays unconfirmed in both directions and needs a component-level or trace-based check. Worth noting that a loading state with no aria-busy would itself be an accessibility gap.
  • F3 — RESOLVED, not a defect. The order's line item reads Price per item $233.00 × Qty 1, line total $186.40 with $233.00 struck through, and the summary reconciles as 233.00 − 149.80 discount + 50.00 shipping = $133.20. So salesRepTopSellers.revenue is the extended list price, gross of discount — the arithmetic is correct. The ACME aggregate confirms it: line revenue $730.00 vs order totals $630.20, a $99.80 gap that is exactly 149.80 − 50.00. Reclassified from "possible arithmetic bug" to a specification question: BL-SR-008 says only that revenue is Money and never states gross versus net, so nothing is violated as written — but a column labelled "Revenue" that reports gross list price overstates revenue whenever a promotion applies. Recommend clarifying the invariant.
  • Empty carts in dated windows — Info, routed to the backend. The tile's displayed 2 is consistent with the two genuinely non-empty carts ($25.00 + $12.00), so there is no UI-visible violation. But the dated windows report ytd count 4 / total $37.00 and prevWeek count 1 / total $0.00 — four carts, two carrying value. That matches BL-SR-006's violation signal ("empty carts counted as active"), though a currency-scoped total is an alternative explanation that cannot be excluded from the storefront. This is a contract question for salesRepCustomerCartStatistics, not a storefront defect.
  • Incidental, low confidence. After selecting a category chip, the Revenue header lost its active-sort marker although the request still carried sort:"by-revenue" — a possible sort-state display mismatch. No case asserts it.
  • Confirmed by design, per the developer's stated scope: no post-mutation cache eviction and no polling, so a widget already on screen does not live-update until the rep navigates back. Deferred pending the TTL / auto-refresh decision the ticket's Notes requested.

SR-HD-014 — error resilience, deliberately left blocked

No environment was mutated · recommend re-homing the assertion

The case requires one widget's operation to fail while its siblings succeed. No admin-side lever produces that: all four sales-rep operations share a single scoped endpoint and one auth scope, so revoking the permission fails all of them and route-guards the hub away — which tests gating, a different assertion, and makes "the other widgets still render" unverifiable by construction. Removing org membership only changes the data: the operations still return 200 with different numbers and no error path. On a shared environment a role-permission change also reaches beyond this session — the other seeded reps, suites 050m / 091 / 093, any parallel run — and restoring a permission set is not atomic.

A zero-risk partial was taken instead: a profile URL for an org the rep does not serve renders a graceful localized empty state — "Customer not found or not in your customers." with a working "Back to my customers" — and the left rail stayed fully interactive, with no stack trace, blank area, crash, or app-origin console error. That covers the case's spirit on the resolver-returns-null path, but not the request-failure path. The assertion belongs in a vitest component test with a mocked erroring Apollo link.
