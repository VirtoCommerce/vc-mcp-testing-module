## Applied — 6 rows across 3 sections

**Two rows asserted the inverse of the behaviour.** Both are the expensive kind of oracle defect: a
false rule reads as authoritative and manufactures findings.

- `ECL-3.2` row 2 claimed an item priced exactly at a range bound is **excluded**. The storefront filter
  component hardcodes inclusion on **both** bounds, the platform's bracket-range syntax is documented as
  inclusive, and a live boundary query returned the boundary-priced items. Row now records the inclusive
  contract and keeps exclusion as the regression it guards.
- `ECL-14.1` row 4's `BL Invariant` cell cited **`BL-CAT-006`**, which governs configurable-product
  *configuration sections* — a different mechanism from the master/variation product model the row
  describes. Removed; the cell now declares a gap (candidate in `bl-proposals-2026-09-03.md` §1).

**One `[THEORETICAL]` promoted.** `ECL-3.2` row 3 (multi-select AND vs OR) → `[OBSERVED]`, verified on
its **own** surface (catalog facets). A same-day exploratory session had observed correct union semantics
on the sales-rep order list, but that is a different surface with a different mechanism (a search-phrase
DSL, not facets), so it was treated as corroboration only and the row was proved where it lives: adding
facet values returned exactly the sum of their individual counts for non-overlapping values, where an
intersection would return zero. That was the section's last `[THEORETICAL]` row, taking it to 4/4
`[OBSERVED]`.

**Two claims narrowed to what the evidence supports.** `ECL-14.1` row 1 no longer lists
`createOrderFromCart` (its return type carries no error-payload surface, so its failures take the
ordinary `errors[]` channel) and its bulk mutation name is corrected to `addBulkItemsCart`. Row 2's
server-side staleness **did not reproduce** — the mutation response and an independent re-read agreed —
so the row now says so instead of asserting a defect, and points at client cache as the thing to
re-derive rather than asserting that either.

**One trigger condition corrected.** `ECL-14.3` row 3 said a member role change applies "after session
refresh"; the token is persisted in browser storage, so a reload rehydrates the **stale** token. The
trigger is the member's next sign-in — which the storefront account guide states outright. A tester who
reloads and reads the old role would have concluded the platform was broken.

**One live-axis caveat closed.** `ECL-3.2` row 1 had rested on docs + source since 2026-08-27 because
that audit's lane could not click — its own amendment said so. Executed on a clicking lane: the sort
survives both a filter-apply and a full reset.

**One correction made to a triangulation proposal before applying it.** `ECL-14.1` row 3's proposed text
asserted `storeId` "can never be silently missing". It is non-null on the catalog and cart queries but
**nullable on ~34 other argument positions**, with `cultureName`/`currencyCode` nullable throughout — so
the proposed wording would have installed a fresh false rule in an entry 368 cases cite, and neutered the
silent-degradation hazard the row exists for. Rewritten around non-uniform nullability. Separately, the
`ECL-3.2` proposals embedded live fixture data (brand codes and result counts); applied entries must be
data-agnostic, so those became relations.
