## Applied (auto, body-only)

**Claim C — the blanket read-only claim was false.** Corrected to the actual conditional binding.

- `Rule:` clause (b) — before: "the custom-code input becomes read-only once a coupon is applied, so
  changing the coupon via that single input requires the user to click 'Remove coupon' first."
  After: read-only **only when its own bound value equals the applied code** (i.e. the coupon was entered
  through that input, or is not among the visible presets); when the applied coupon **is** a visible preset
  card the input resets to empty and stays editable — and the single-slot guarantee still holds because the
  submission goes through the same `applyCoupon` path.
- `Verify:` — before: "after applying A the input is read-only and only 'Remove coupon' is offered."
  After: split by provenance of A (visible-preset ⇒ empty + editable, by design; custom-entered or
  non-visible ⇒ mirrors A and locks).
- `Violation signal:` — before: "the custom input remaining editable while a coupon is applied" (this
  wrongly made correct behavior a violation). After: the **preset** card's own input becoming editable
  (a binding regression), or the custom input showing a stale code / failing to reset.
- `Source:` — added the `coupon-card.vue` readonly expression and the `coupons-section.vue` `watchEffect`
  mirroring rule; qualified the `useCoupon.ts` order as "on `dev` HEAD" with a pointer to the held skew.
- `Amended:` — new 2026-08-05 stamp; prior 2026-07-22 stamp preserved as a `Previously amended:` line.

## Applied — the two that mattered

**`BL-AUTH-015` — two defects in yesterday's unattended text.** (1) It said an empty **membership** list
skips the accessibility filter; the skip is actually keyed on an absent userId or an empty **associated-org**
list. With orgs but no membership rows the filter *does* run and falls through to the contact's status — so
the old Violation signal ("a user with associations but no membership rows is denied every org") would have
**filed a bug against correct behaviour** for a contact whose own status is blocking. Now conditioned on a
non-blocking contact status. (2) Resolution has an unrecorded **write side effect**: the resolved org — and,
because fallback rewrites the request parameter, a *silently substituted* org — is persisted back onto the
contact's `CurrentOrganizationId` (skipped for impersonation grants). A test treating that field as a stable
precondition is racing its own earlier grants.

**`BL-AUTH-006` — the tier list was ungrounded.** Of the five names presented as privilege tiers, only one
existed as a data role on the audited build and one had no referent at all, making the `Verify` steps
unexecutable. Replaced with the grounded distinction — reserved system roles vs per-deployment data roles vs
an unauthenticated state — with **every behavioural assertion preserved verbatim** (45 citing cases).

Also applied: `004` (pre-fill is config-gated and off by default, and sources the last **order**, not the
address book); `013`'s "Rejected/Deleted are source-only" caveat **retired** (all three codes observed live);
`014`'s "not-yet-merged PR" caveat **discharged** (merged + re-confirmed). `012`/`013`/`016` gained `Verify`
traps for failure modes that produce a **vacuous pass or a false FAIL** — most importantly that the org-lock
400 only appears when the locked org is the user's *only* accessible one, and that error counts must come
from `errors[]`, never the response's `count` field.
