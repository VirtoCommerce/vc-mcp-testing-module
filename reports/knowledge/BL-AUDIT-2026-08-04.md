## Applied to `business-logic.md` (see the git diff)

- **BL-AUTH-015** (new, P0) — the **5-step** resolution chain over *accessible* orgs. The candidate started
  at `CurrentOrganizationId`; source shows **two earlier steps** (explicit request parameter, then the
  principal's existing claim), so the promoted rule is the corrected 5-step chain.
- **BL-AUTH-016** (new, P0) — fallback-first / single-code / lock-beats-status, **plus the condition the
  candidate did not carry**: on a password grant the refusal is returned *only* when no accessible fallback
  org remains, and a grant resolving no org at all **succeeds org-less** rather than refusing.
- **BL-AUTH-013** (amended) — extended from the LOCK axis to **both** axes with the per-status code table,
  and re-scoped to *which* code rather than *whether* a refusal happens.
- **BL-AUTH-012** (amended, Verify only; Rule untouched and still correct) — **highest-value edit of this
  run.** Its Verify asserted HTTP 400 for a locked org unconditionally; on this build a password grant from
  a **multi-org** user naming a locked org returns **HTTP 200** on the fallback org, so the step was a false
  FAIL for every multi-org fixture. Now scoped to a single-accessible-org fixture or a non-password grant.
- **BL-B2B-012** (new, P1) — decline/revoke are **status transitions on a persistent row**; the removed
  status is a status, not a deletion; re-invite gated on the reinvitable pair, so an already-invited
  membership is resend-only.
- **BL-B2B-013** (new, P1) — three-tier effective-status resolution (membership → contact → default), the
  four-value dictionary set, and **status vs lock as separate axes**.
- **Coverage Summary** — only the three derived count cells my additions invalidated (AUTH row, B2B row,
  Total 188→192 / P0 51→53 / P1 103→105). The protected Severity-Tags legend was not touched.
