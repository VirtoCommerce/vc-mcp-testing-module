## Executive Summary

VCST-5028 replaces Virto's **global** user roles + lockout with a **per-organization** `OrganizationMembership` entity, so one person can be a maintainer in Org A and an employee in Org B with independent roles and independent block state — and an org block no longer locks the user out everywhere. The data-layer behaviour is correct and verified (per-org JWT isolation, org-scoped role change, org-scoped lockout that leaves the global account untouched, Admin SPA widget governance). **However, the primary user-facing flow is broken:** an org-maintainer's permissions reach the JWT but the `me`/`GetPageContext` projection returns `permissions:[]` after org-switch, so the storefront hides the Invite button and all per-member actions — maintainers cannot govern their org (BUG-A, High). A second defect leaks the DB name and persists orphan records on bad input to the REST create endpoint (BUG-B). The xAPI write mutations are additionally unverifiable end-to-end because the deployed PR#135 build is stale/schema-only (`MISSING_METHOD`).

## 1. System Architecture — old vs new

**Old:** roles lived on `ApplicationUser.Roles` (global); blocking called `IAccountService.LockAccountByIdAsync` → set global `ApplicationUser.LockoutEnd`. A block/role in one org applied to every org the shared user belonged to.

**New (`OrganizationMembership`, one row per user×org):**
```
OrganizationMembership : AuditableEntity
  UserId            // security-account id (NOT contact/member id)
  OrganizationId, OrganizationName
  IsLocked, LockoutEnd, IsCurrentlyLocked
  Roles : [OrganizationMembershipRole{ RoleId, RoleName }]
```
- Role change / lock / unlock now write the **single membership row**; the global account is never touched.
- xAPI mutation handlers derive `OrganizationId` from the JWT `organization_id` claim (`context.GetCurrentOrganizationId()`), so the caller can only act within their active org.
- Login → org-switch mints a **per-org bearer**: `organization_id` claim + org-scoped `permission[]` projected from that membership's roles.

Source: `vc-module-customer` PR#300 `OrganizationMembership.cs`, `OrganizationMembershipController.cs`; `vc-module-profile-experience-api` PR#135 `ChangeOrganizationContactRoleCommandHandler.cs`, `Lock/UnlockOrganizationContactCommandHandler.cs`, `ContactType.cs`, `ProfileSchema.cs`; `vc-frontend` PR#2315 `useOrganizationSwitcher.ts`, `members.vue`, `sign-in-form.vue`.

## 5. API Analysis (summary)

**REST `OrganizationMembershipController`** (`/api/customer/organization-memberships`) — `POST /search`, `POST /` (create), `GET/PUT /{id}`, `DELETE` (bulk `?ids=`), `POST /{id}/lock` (optional timed `lockoutEnd`), `POST /{id}/unlock`, `GET /user/{userId}/count`, `GET /user/{userId}/org/{organizationId}`. Permissions: `customer:organization-membership:{read,create,update,delete}`. Create body `{userId, organizationId, organizationName, roles:[{roleId,roleName}]}` — `userId` = security-account id.

**xAPI** — read: `ContactType.rolesInOrganization(organizationId)`, `ContactType.isLockedInOrganization(organizationId)` (no `organizationMemberships` field). Mutations (org from JWT, perm `xapi:my_organization:edit`): `changeOrganizationContactRole(memberId, roleIds)→CustomIdentityResultType`, `lockOrganizationContact(memberId)→ContactType`, `unlockOrganizationContact(memberId)→ContactType`. REST exposes timed lock; xAPI locks indefinitely only.

**Top API fixes:** (P0) add `userId`/`organizationId` validation guards on create+update → kills the 500/leak + orphan; normalize lock/unlock error shape; re-fetch on `PUT`. (P1) add `organizationId` to the search criteria; deprecation-alias the `userId→memberId` rename; add timed-lock parity to xAPI. (P2) `GET /user/{userId}` list; unique index on `(userId, organizationId)`; access guard on the new read fields.
