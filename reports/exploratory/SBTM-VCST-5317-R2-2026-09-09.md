## M1 (P0) — the mobile contradiction, SETTLED. Round 1 resolved it the wrong way.

**Viewport actually achieved: a genuine 375×812**, verified from the PNG header of `R2-M1-01-viewport-check.png` (`width 375 height 812`), not asserted. `design-report.md` F-U2's *"375px unreachable — clamps at 500px"* is **lane-specific to Chrome DevTools MCP**; `page.setViewportSize` reaches 375 px headed on `playwright-chrome`. No 500 px substitution anywhere below.

**REFUTED — Round-1 F3, checklist G15 and net-new P3**, all claiming *"at 375 px there are no rows at all"*. On a **multi-org** account, `hamburger → Corporate → "My organizations"` **exists and renders both organizations as radio rows**. Round 1's own Step-4 screenshot filenames were the correct half of its self-contradiction. `mobile-navigation.md` §5's *"ABSENT"* is untouched — measured on a single-org member, where absence is correct; its §11 lists the multi-org shape as an open gap, and **that gap is now closed by observation.**

**CONFIRMED — scenario 14's P0 hypothesis in full.** At **V2** (TechFlow locked, BuildRight active), same account, same minute:

| | Desktop 1920 (`top-header-organizations.vue`, patched by #2469) | Mobile 375 (`multi-organisation-menu.vue`, **untouched** by #2469) |
|---|---|---|
| Locked TechFlow row | `option … [disabled]`, greyed, **padlock rendered** | `radio …` **enabled, full-contrast, no padlock, no lock indicator** |
| Tappable | no | **yes** |
| Evidence | `R2-M4-01-desktop-V2-locked-row-disabled-padlock.png` | `R2-M1-02-mobile-375-V2-locked-row-not-flagged.png` |

The mobile radio's `value` is `96f109a7-9010-4691-b6a1-bef25cca3d04` — the **locked** org id, bound as a selectable option. Tapping it, reproduced twice, two different failures:

| Run | Session | Response to `POST /connect/token` (`grant_type=refresh_token` + `organization_id=96f109a7…`) | Outcome |
|---|---|---|---|
| 1 | live session whose refresh token the lock write had already revoked | `400 invalid_grant` — *"The specified refresh token is no longer valid."* | hard redirect `/sign-in?returnUrl=/account/dashboard` |
| 2 | **fresh sign-in**, valid refresh token | `400`, **exactly one** `errors[]`, `code: user_is_locked_in_organization`, *"Your access to organization '96f109a7…' has been blocked. Please contact your organization administrator."* | **identical** redirect to `/sign-in` |

**Run 2 is load-bearing and separates server from client cleanly.** The server behaves exactly as `BL-AUTH-013` specifies — right code, one error, a ready-made user-facing message naming the org. The defect is **entirely client-side**: `multi-organisation-menu.vue` has no `:disabled`, no padlock and no `selectOrganization()` guard, fires the switch anyway, discards a perfectly good 400, and **signs the user out of everything** — including the org they were legitimately working in. One console error (`400 (/connect/token)`); no other console error, no 5xx, no other 4xx all session. **Mitigation, real but partial:** the BuildRight cart ($1,299.99) **survived** and was intact on re-auth — the cart is server-side. The user loses the session and their place, not the basket.

## M2 (P0) — scenario 18: NO LEAK on either field; the vector does not exist

Canonical runner only (`scripts/graphql/graphql-runner.ts`), 4 live runs; scratch CSV and evidence dirs deleted, nothing written under `regression/suites/`.

1. **The `userId` argument is INERT** `{OBSERVED}`. On `organization(id:, userId:)` under an org-scoped TechFlow-admin token the answer was identical whether `userId` was omitted, the caller's own, the **ALT user's (who IS locked in TechFlow)**, or a bogus all-zeros GUID — `isLockedForCurrentUser:false`, `myStatusInOrganization:Approved`, no `errors[]`, every time. Same on `contact(id:, userId:)`. `GetCurrentUserId()` resolves from the **authenticated principal**. The bogus GUID returning a clean correct answer rules out coincidental equality. No other user's state is disclosed — an inert-argument contract smell, not a leak.
2. **A document can carry only ONE `organization`/`contact` resolution** `{OBSERVED}`. Every two-alias document — both orderings, both queries — returned first-alias data plus `null` for the second with `{"message":"Error trying to resolve field '<alias>'","extensions":{"code":"ARGUMENT"}}`, inside **HTTP 200**. First-wins, order-symmetric, and **two aliases with identical arguments fail the same way**, so the failure is not `userId`-dependent. Two resolutions cannot contend for the loader cache at all.

**Per-org discrimination is correct** `{OBSERVED}`: one `contact.organizations` response returned BuildRight `false` and TechFlow `true` simultaneously — the org-id key works, orgs do not collapse. **Provenance:** both fields behaved identically on every leg and the second-alias failure reproduces on `contact`, which #145 does not touch ⇒ **PRE-EXISTING PATTERN, not introduced by #145.** Scenario 18's P0 framing is **not confirmed**; de-escalate to a contract-hygiene note. **Mechanism refinement:** the likeliest cause of `ARGUMENT` is the very thing scenario 18 named — a **constant-named** loader registered twice in one document. If so the constant name is real and does bite, but it surfaces as a **hard error, not a silent leak** — the safe direction — and it reproduces on the pre-#145 `myStatusInOrganization` path, so it is platform-wide. **Premise honesty / NOT REACHED:** the backend-lane user's own answer was never `{OBSERVED}` here (every route closed: `contact(id:<foreign>)` → `ARGUMENT`, `userId` inert), so a third genuinely-unlocked account (**TECHFLOW_ADMIN**, touching neither fixture lane) was substituted, giving a fully-`{OBSERVED}` asymmetric pair: ALT `true` vs admin `false`. Also NOT REACHED: `organization(id:, userId:)` under the ALT token — `Forbidden` on every variant, that alias declaring no `organization_id`. Every error arrived inside HTTP 200 in `errors[]`.

One caveat: the design report's stated *mechanism* (*"`title` becomes the accessible description"*) is **unconfirmed** `{HYPOTHESIS}` — no `title` tooltip rendered on a ≥2 s hover, so `aria-describedby` + hidden text is likelier.
