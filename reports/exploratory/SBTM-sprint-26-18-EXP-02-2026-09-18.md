## Oracle Feedback

Rows 1–4 return `Oracle ref: NONE`. Proposals routed to `/qa-review-oracles` (`ba-system-analyzer` is the sole writer — **no oracle file was edited**; no `BL-*`/`ECL-*` id was invented).

- **Proposed ECL `[THEORETICAL]` pattern (from #1):** *"A capability ships behind a build-time flag that is off in the deployed artifact → the feature is 'Done' in the tracker, its code is an ancestor of the deployed head, and it is nonetheless inert at runtime. Version and ancestry checks both pass; only a runtime probe distinguishes shipped-and-active from shipped-and-dark."* This is a strictly stronger trap than EXP-01's "released ≠ deployed", because here the code **is** deployed. Same class as this repo's own `NOT_DEPLOYED` rule, one level deeper.
- **Proposed BL-SR candidate (from #3):** *"A navigational affordance must not carry the rep across the creator-scoped and membership-scoped order families without changing its label or signalling the scope change."* BL-SR-002 fixes the two scopes and is not violated by either surface; nothing currently governs a control that joins them, which is precisely where a rep would misread "All orders" as completeness.

## Observations

- **Charter scenario 1 (throttled/blocked plugin manifest) — NOT REACHED, and its premise is void on this build.** There is no discovery request to throttle (#1). Reaching it also requires request interception, which the real-user rule puts out of bounds for this lane; it needs a build with the flag on plus a DevTools-lane brief.
- **Charter scenario 2 (rep → non-rep in the same tab) — NOT REACHED.** Two reasons, stated separately as the charter requires. (a) **Premise void:** there is no plugin registration to go stale, so a leak via that mechanism cannot exist here; the hub routes are static and gated by `isSalesRepsEnabled()` + permission guards, a different mechanism. (b) **Attribution would have been undecidable anyway:** the deployed platform's entire token-issuance/revocation pipeline is unmerged PR #3108, so any session-boundary anomaly could not have been separated from that rewrite — and per the charter I would not have filed it as a Sales Rep defect. I signed out of the account menu but did not complete the second sign-in before the time-box expired.
- **Charter scenario 3 — REACHED, clean** (net-new #2). **Charter scenario 4 — REACHED** (net-new #4), with the caveat that the dashboard exposes no period *filter* control: WEEK/MTD/YTD are three separate stat cards, so "chip state survives a period-filter change" has no control to actuate. Only the browser-back half was testable.
- Rep context observed: active org **AcmeWest**, org switcher lists 5, sidebar badge 5, JWT `permission: sales-rep:access` — consistent with the domain map's rev-3 §3b/§3d.
