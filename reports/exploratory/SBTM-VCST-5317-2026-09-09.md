## `{OBSERVED}` per `{HYPOTHESIS}`

**Scenario 17 — REFUTED, cleanly.** As the backend-lane user at V2 (TechFlow locked):
- `me.contact.organizationsIds` = `["96f109a7…(LOCKED)", "23525b44…"]` — the locked id **is** returned, and `organizations.totalCount` stayed **2** with `isLockedForCurrentUser: true` on the locked item. Post-#145 as designed.
- Naming that locked id in an org-scoped read is **refused**: `organization(id: <locked>)` → `errors[0].extensions.code = "Forbidden"`, `"Access denied."`, `data.organization` null.
- **The discriminator:** the same query against the *unlocked active* org (`organization(id: <BuildRight>)`) returns **200, 0 errors, data present**. So the refusal is lock-specific, not a blanket customer-principal denial — the authorization path does re-evaluate the lock per org.
- `currentOrganizationAddresses` → 200 (current org only, no id to spoof). `organizations` (top-level) → `Forbidden` for the customer principal.
- **No claim-provider bypass found.** Nothing downstream treated the locked org as accessible. `organizationsIds` is now a *membership* list, not an *access* list — a valuable negative that grounds scenario 17 at P1-regression value rather than P0.

## Mission 3 — the reverse edge (session kill)

**The user sees nothing.** Signed in and active in the unlocked org (BuildRight), I locked the *other* membership (TechFlow) from the seeder, then kept using the storefront: sidebar → `/account/orders` client-side nav loaded normally, **13 `POST /graphql` all 200**, no redirect, no 401 wall, no half-render, no lost cart. Re-opening the account menu showed TechFlow already `[disabled]` — the row updated with **no re-login**. So `TerminateAllUserSessions(userId)` does not evict the live storefront session for a *sibling*-org lock; `BL-AUTH-012` holds and the session survives too. The model's "the user must re-authenticate" is **not** what a user experiences here.

## Model amendments (evidence-backed)

- **A1 — the storefront version gap is closed.** The footer prints `Ver. 2.58.0-pr-2469-83d6-83d6e5d5` on every page. The pre-flight recorded "the storefront exposes no version endpoint … semantic theme version is a **known gap**" — it does expose one, in the DOM, and it names the PR. Replace the bundle-hash argument with this string.
- **A2 — the switcher is not a top-header control.** It lives **inside the Account-menu popover** (`listbox "Organizations"`, options per org). Any case whose steps say "click the org switcher in the header" must first open the account menu. Desktop-only.
- **A3 — reverse edge "lock → all sessions terminated" is not user-visible for a sibling lock** (Mission 3). Amend the reverse-edge table: the *token* is revoked server-side; the storefront session and the live page keep working, and the row re-renders disabled on the next fetch. Scenario 17's session half is a **negative** result, not an absent one.
- **A4 — scenario 14 inverts.** The mobile hypothesis was "locked rows stay tappable with no padlock and no guard". Live: **there are no rows** — mobile renders the current org as static text and exposes no switcher (F3). The P0 framing (unguarded mobile row reaching L7) is refuted; the real gap is a missing capability. Re-scope 14 from `PARITY / P0` to `SPEC-GAP / P2`.
- **A5 — V4×L6 is `WAIVED — vacuous`, not `GAP`** (Mission 2).
- **A6 — scenario 17 needs its discriminator recorded.** A "Forbidden" on the locked org proves nothing on its own; only the *unlocked-sibling* control (200 + data, same query shape) makes it a lock-specific refusal. Any promoted case must carry both legs.
