## Oracle Feedback

All five rows are `Oracle ref: NONE`. Two proposals routed to `/qa-review-oracles` (**not** edited here; `ba-system-analyzer` is the sole writer):

- **BL-AUTH-005 amendment** — it names `read_prices` as an Orders extension but says nothing about what a *denied* read looks like. The observed contract is specific and testable: amounts zeroed on the wire, `withPrices:false` beside them, and a non-numeric `#.##` mask in the UI — never `0.00`. This would give N1/N2/N3 a citable oracle instead of leaving the negative space uncited.
- **BL-PRICE-006 extension** — it warns a product must never show `$0.00` after pricelist deletion; the same reasoning now applies to a *restricted* order total. The Orders UI gets this right; the wire deliberately does not (it sends `0` + a flag), which is defensible but unstated, so a consumer ignoring the flag would look correct to a reviewer.

## Bugs Found

**One, reported here only — nothing filed externally.**

**Revenue statistics bypass `order:read_prices` (N1).** A back-office user provisioned as "can work orders, must not see money" sees the store's entire revenue history the moment they also hold `order:dashboardstatistics:view`. Reproduced on both layers in the same session: API responses identical between restricted and control tokens, and the Admin home dashboard rendering the figures under the restricted user's own name.

**Severity: Medium, deliberately not High.** It is a *permission-composition* hole, not an unauthenticated leak — a second permission is required, and `order:dashboardstatistics:view` is plausibly read by whoever grants it as "may see the sales dashboard", i.e. as its own money-visibility grant. The honest framing is that the two permissions have never been reconciled: VCST-3912 routed everything that *returns an order* through the new service, and the dashboard returns aggregates computed over order totals rather than orders, so it was never in that net. Whether aggregates are in scope is a product decision, and I did not find a VirtoOZ page that settles it.

**Attribution:** this is attributable to **VCST-3912's scope boundary**, not to platform PR #3108. The claims pipeline demonstrably works on this build — the same two tokens produced correctly *different* results on six other endpoints in the same minute, which is exactly the control PR #3108 would have broken if it were at fault.

## Risk Areas

- **The wire contract is "zero + a flag", so every consumer is a potential leak-by-omission.** The Admin UI reads `withPrices` and masks; a consumer that does not read it displays `0.00` and looks plausible. Integrations, reports and any custom Admin widget are unreviewed on this point.
- **Aggregate and derived surfaces generally.** The dashboard is the instance I found; the class is "anything that computes over order totals without returning an order". Change-log `detail` strings are the other member of that class I could see but not exercise (the available records were `Added`, carrying no price).
- **Invoice generation (N4)** is 500 on this environment, so the highest-value price-rendering surface in the module is currently unverifiable.

## Observations

- **Paths the PR claims that this deployment does not expose:** `POST /api/order/customerOrders/indexed/search` → **404** for both readers (indexed search not enabled here), and the platform export registry `/api/platform/export/knowntypes` → **404** with no export endpoint in the Orders swagger. So the PR's *indexed search* and *export/import* claims are unverified on this build — not failed, unreachable.
- `GET /api/order/customerOrders/{id}/changes` is permitted to the restricted reader; the available audit records were `Added` and carried no monetary value, so it neither passed nor failed. Firefox behaved as a full click lane throughout (no timeouts), but `browser_type`/`browser_click` need a `target` argument in addition to `element`/`ref`.

## Questions

1. Are revenue **aggregates** intended to be in scope of `order:read_prices`, or is `order:dashboardstatistics:view` itself meant to be the money-visibility grant? This decides whether N1 is a bug or a documentation gap, and I could not settle it from the ticket.
2. Is `#.##` an intentional, localizable mask, or a formatter artifact of rendering `0` with a null currency? It reads as deliberate but appears in no spec I found.
3. Is the invoice PDF path (N4) meant to route through `ICustomerOrderDataProtectionService`? The ticket does not list it among the covered paths.

## Charter-from-Gap

**Proposed EXP follow-up — "aggregate and derived money surfaces".** Same fixture pair, 30 min, targeting everything that computes over order totals without returning an order: dashboard statistics (confirm N1's fate), the change-log `detail` text on an order whose price was *edited*, any reporting/notification template that interpolates a total, and the xAPI GraphQL order surface this session did not reach.
