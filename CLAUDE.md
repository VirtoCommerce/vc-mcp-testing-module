# CLAUDE.md

## Project Overview

**Agentic QA system** for the Virto Commerce B2B e-commerce platform. Tests are executed through natural language prompts via MCP servers (Playwright, Chrome DevTools) — LLM-powered browser automation, NOT traditional `.spec.js` files. Prompt templates live in `vc/shared/docs/prompts/`.

This repo hosts the **`vc-tools` Claude Code marketplace** (`.claude-plugin/marketplace.json`), which distributes **two plugins**. The first is **`vc-fix`** (`plugins/vc-fix/`) — the bug-lifecycle slice: `/project-init`, `/qa-bug`, `/qa-fix` (+ its `fullstack-backend`/`fullstack-frontend`/`backend-reviewer`/`frontend-reviewer` dev team), `/qa-verify-fix`, `/qa-monitoring` (+ `monitor-triage-agent`), and `/vc-self-check` (the self-diagnostics subsystem — see below) + `/vc-feedback` — 10 agents, 16 skills, 8 commands. Teammates/customers add the marketplace with `/plugin marketplace add VirtoCommerce/vc-mcp-testing-module`, install via `/plugin install vc-fix@vc-tools`. `vc-fix` is **fully self-contained, not repo-coupled** — its own `plugins/vc-fix/knowledge/`, `.claude/rules/`, `config.js`, `scripts/lib/`, `package.json` etc. are duplicated from the repo root, not referenced in place. This is deliberate: Claude Code doesn't document a reliable way for a plugin's commands/skills to resolve bare relative paths against "wherever the plugin got installed" (no `${CLAUDE_PLUGIN_ROOT}`-equivalent; paths resolve against the *user's* CWD, which may be an unrelated project) — see `plugins/vc-fix/skills/qa-fix-routing/SKILL.md` for the finding. `qa-fix-routing/` additionally resolves its own data-file paths (`fix-repos.json`, `.module-registry.cache.json`) off `import.meta.url` rather than `process.cwd()`, so at least that piece works regardless of working directory. `/project-init`'s own onboarding flow now handles the same split explicitly: `plugins/vc-fix/skills/project-init/lib/paths.mjs` separates `outputRoot()` (`VC_FIX_HOME || process.cwd()` — where ALL generated project state lands, symmetric with the readers) from `pluginRoot()` (`CLAUDE_PLUGIN_ROOT ||` resolved-from-`import.meta.url` — read-only plugin assets, never a write target), so an installed plugin writes `project-profile.json`/`.env.*`/`.mcp.json` into the *project*, not the versioned marketplace cache. `gen-mcp` copies the Playwright MCP configs into the project's `config/` because `${CLAUDE_PLUGIN_ROOT}` does not expand inside a project-level `.mcp.json`.

The second plugin is **`vc-perf`** (`plugins/vc-perf/`) — the three-layer performance loop: **L1** BenchmarkDotNet A/B, **L2** a k6 load harness + `dotnet-counters`, **L3** `dotnet-trace` allocation/CPU/DB attribution, plus a `perf-analyst` agent that ranks optimization candidates and a `perf-loop` orchestrator. It **depends on `vc-fix` (`>=0.7.0`)** and reuses its onboarding, routing, and backend dev/review agents rather than duplicating them; advisory only, never a CI gate. **Each plugin versions and tags independently** (`vc-fix` `0.8.6`, `vc-perf` `0.2.6`, catalog `0.9.4`) — the marketplace's own `version` is the catalog's, not a plugin's, and a dependency range resolves against the per-plugin `{name}--v{version}` git tag, so a version bump without its tag silently strands dependents (`docs/release-process.md` §Step 1 + §Step 5a).

**Self-diagnostics — capture, judgement and surfacing are THREE separate layers (VCST-5582 H).** The collector **records that something happened and is forbidden from deciding whether it matters**; `/vc-self-check` assigns severity; the `Stop` hook chooses only tone and timing. This inverts the original design, where `emitSpan`'s non-success test was simultaneously the *retention*, *analysis-scope* and *surfacing* decision (`state.flagged[]` was the only thing the diagnostician read), so any signal the deterministic classifier did not recognise at span close **ceased to exist** — a real `/project-init` run printed a **WARN** in its own readiness table (the Azure Bug field contract was never scanned: HTTP 400 → stderr → exit 0) and self-diagnosed `no plugin issues detected` with `spanCounts:{success:31}`, `flagged:[]`. Every anomaly signal, however minor, is now a durable **`type:"obs"` record** with **no severity/verdict field** — closed `class` vocabulary, slugified `subject`, taxonomy `code`, aggregated by signature (first sighting appends, later ones bump `count`; caps announce themselves as `capture_truncated`, never truncate silently). New capture sources: the transcript's `toolUseResult` sidecar (**stderr on an exit-0 tool**, `interrupted`, `Exit code N`), self-labelled degradation prose (`unverified defaults`, `falling back to`) in stdout **and** stderr, every non-PASS row of `verify-access.mjs`'s readiness table + every failed scan in `discover-tracker.mjs` (via the collector's new **`obs` subcommand**, `skills/project-init/lib/diag-obs.mjs`), the written profile's SHAPE (`skills/project-init/assert-profile.mjs`), signals on spans that end `success`/`recovered`, sub-agent **sidechain** errors (aggregate-only), and the collector's own health. Two hard invariants make the original failure unrepresentable: `verdict:"clean"` requires `observations.total === 0 && flaggedTotal === 0 && !scanErrors`, and any `self_reported_warn`/`_fail` forces at least `attention`. `decision.verdict` (`clean`/`observed`/`attention`/`degraded-collector`) now describes the **run** and is derived from counts alone; `surfaceDecision`/`suppressReason` describe the **UI choice** — conflating them is how a `failed` span once landed in a record that called itself `clean` (two such sessions are still on disk). The status line has **three** states so the hook can stay quiet without ever saying "clean" while observations exist. Surfacing is bounded by a **HARD routing class set** (data, mirrored in the oracle §1e) plus per-signature dedup — everything outside it is still recorded, still counted, still analysed. The set is `self_reported_fail` · `degraded_artifact` · `script_exit_nonzero` **from a plugin-owned script only** (`obs.pluginOwned` — anchored to the installed plugin root: a `$CLAUDE_PLUGIN_ROOT/{hooks,skills,scripts}/…` reference or an absolute path under `pluginRoot()`, **NOT** a bare `PLUGIN_SCRIPT_RE` dir-name match, which `opSubject` still uses for the `subject` label; so a client's own failing `node ./scripts/build.mjs` under its own `scripts/` is recorded but never arms the plugin's diagnostician) — plus, outside the observation stream, a flagged span, a 👎, and a **grown occurrence count** (`obsSurfacedCount` records the count a signature routed AT, so a recurrence re-qualifies instead of being silenced for the session; §1f rule 5). `self_reported_warn`, `http_non2xx` and `collector_contention` were **demoted out of routing** — the old set fired on essentially any new signal, so a run whose command span ended `recovered`, whose deliverable landed, and whose findings were all S2/S3 friction still cost the operator a whole extra turn; they still forbid the word "clean" (a verdict rule, not a routing one) and are still diagnosed on the next `/vc-self-check`. A turn now emits **ONE info line and at most ONE question**: the cleanup **question was removed** (the reproduction asked verdict + delivery offer + a 3-option cleanup prompt at once, so the delivery offer had to be re-asked later), because the 24 h age-cap already reclaims leftovers unprompted — the artifact count now rides the info line as data, not a decision. Deletion now requires the *analyze* step: a session holding an un-diagnosed finding survives the 24 h age-cap and `purge-inactive` (`--force` overrides). Judgement rubric + correlation rules: `knowledge/diagnostics/skill-expectations.md` §1e/§1f.

**Self-diagnostics subsystem** (VCST-5475–5479, evolved into a client→vendor feedback loop by VCST-5509) — a two-tier way for a client-installed `vc-fix` to observe whether its OWN skills ran correctly and (opt-in) report quality issues back to VirtoCommerce, without ever mutating the client install or leaking client code. **Tier A** (passive, **opt-in** — captures only when `project-profile.json` sets `selfDiagnostics: true`, default off): `hooks/session-telemetry.mjs` wired via `hooks/hooks.json` — `SessionStart`→init, `UserPromptSubmit`→prompt (`/vc-feedback`), `PostToolUse[Skill]`→record, `SubagentStop`→agentstop, `Stop`→finalize. It reads the session transcript delta at each skill boundary + Stop and records deterministic, outcome-classified span signals (tool errors, denied permissions, hook failures, STOP/BAIL markers) to `<outputRoot>/.vc-fix/diagnostics/<session_id>.jsonl` (`outputRoot = VC_FIX_HOME || cwd`, per `paths.mjs` — NEVER the plugin dir; `.vc-fix/` is gitignored). Secrets are redacted; it never throws/blocks. **Tier B** (on-demand): `/vc-self-check` (`skills/vc-self-check/`) reads the telemetry + transcript against the oracle `knowledge/diagnostics/skill-expectations.md` (per-skill expected phases/gates + S0–S3 rubric) **via the `self-check-diagnostician` subagent, which returns a validated finding STRUCT** — it writes **NO local report file** (the old `DIAG-*.md`/`.json` was removed in the PR #172 rework; the oracle/jsonl/transcript never enter the main conversation). The `Stop` finalize runs `/vc-self-check` **silently via a tail-trigger** (`{decision:"block"}`, no `AskUserQuestion` modal) **only when the Tier-1 classifier flagged ≥1 span** (outcome `failed`/`degraded`/`silent_suspect`) or a `/vc-feedback` 👎 was recorded that session; a clean run prints one `vc-fix self-check: no plugin issues detected` line, and a plain development session with no plugin skill never triggers it (opt out with `VC_FIX_DIAG_CONSENT=off`; a session whose transcript scan errored is reported `degraded-collector`, not clean). It is model-invocable (no `disable-model-invocation`) so the tail-trigger can auto-run it, but never auto-triggers unprompted — recursion/re-nag is blocked by the `selfCheckSeen` one-shot guard + per-signature dedup + the collector dropping its own `vc-self-check` spans. `skills/vc-self-check/deliver.mjs` (`/vc-self-check deliver`, run by the `self-check-deliverer` subagent) turns the validated finding struct into a consent-gated contribution to `VirtoCommerce/vc-mcp-testing-module`, routed by GitHub-token rights via `probe-lib.mjs` — **two routes only, `issue` / `local`**: any authenticated token with issue rights (push/maintain/admin included) files a **GitHub Issue**; only a missing token, a probe that fails twice, or read scopes carrying neither `repo` nor `public_repo` stay local. The former `pr`/`fork-pr` routes were **removed**: both were hand-offs that printed `git`/`gh` commands and sent nothing, so the MORE rights a token had the LESS was delivered (a `maintain` token produced `sent: false, handoff: true` while an issues-only token auto-filed) — and a telemetry report is not a code change, so it never needed a PR. A transient probe failure is **retried once** (`probeWithRetry`) before falling back to `local`, and the `reason` says so; everything operator-actionable also travels as a `nextSteps[]` field in `--json`. **§2a client-code containment is enforced by a default-deny CLOSED SCHEMA, not a denylist:** the outbound artifact is built ONLY from a validated `UpstreamSignal` struct (`skills/vc-self-check/upstream-reduce.mjs` → `reduce`/`validateUpstream`/`fingerprintStruct`; spec `knowledge/diagnostics/upstream-schema.md` + ADR `adr-upstream-default-deny.md`) whose every field is a closed-vocabulary enum or number — skill/**subject**/**blockedDeliverable**/verdict/severity/outcome/signal-class/struggle/error-**taxonomy-code**/tool-family/repo-**kind**/counts, ZERO free-text fields. **Schema v2** added `subject` (a closed `SUBJECTS` enum naming WHICH operation misbehaved — `ado_create_workitem`, `browser_login`, `github_search_issues`, …) and `blockedDeliverable`, because a v1 row read `other | BROKEN | S1 | …` and could not distinguish an Azure-Boards field-contract blocker from a credential-handoff gap; a row now renders `S1 · qa-bug · ado_create_workitem · blocked`. `subject` is a **mapping, never an echo** (`subjectEnum`, `_`-boundary-delimited markers so a client repo name containing e.g. "checkout" cannot steer the bucket). **Input is a validated struct, not a parsed report (PR #172 rework).** `deliver` receives the finding STRUCT the `self-check-diagnostician` subagent produced (on stdin / `--input <file>`), re-validated by `validateUpstream`; the old `--diag` + DIAG-markdown-table + sidecar-`DIAG-<sid>-<ts>.json` source-precedence chain is **GONE** — parsing a human-written `.md` for a closed vocabulary was the shared root cause of the header-backtick and `skill: other` defects, fixed by deletion. `reduce()` (the pure reducer the tests exercise) reads ONLY the structured collector jsonl — span records + **`type:"obs"` observation records** + feedback verdicts; the diagnostician's free-text fields (`signal`/`rootcause`/`fix`) and `/vc-feedback` prose NEVER enter the upstream path (feedback travels as 👍/👎 counts only), error TEXT is classified locally to a code (only the code travels), and repo/module/org NAMES are never sent — so the client-data-leak class that recurred across three review rounds is impossible by TYPE. `redact()` (shared `hooks/redact.mjs` secret rules) still scrubs the local persist path; the former free-text client-shape scrubbers (`scrubText`/`isClientSpecific`/`containsClientShape`) were **removed as dead code** (PR #143 review round 2) — with an enum-only upstream artifact there is nothing free-text to scrub, so the closed schema is the sole upstream guard. Local diagnostics are **ephemeral** — the lifecycle is log → analyze → contribute → **delete**: on a successful Issue delivery (`--confirm`, or a dedup already upstream) `deliver` removes the processed session's own artifacts (`<sid>.jsonl` + `<sid>.state.json`; that session only, never others; the `<sid>.surfaced.json` tombstone is deliberately KEPT so a rebuilt session never re-nags an already-delivered defect; `--keep` retains). The `local` route (nothing sent) deletes nothing — it prints the ready `--purge` cleanup command. **Canonical copy: `plugins/vc-fix/`.** The **self-diagnostics subsystem is now kept in sync across both surfaces** (PR #143 R2): `hooks/redact.mjs`, `hooks/session-telemetry.mjs`, `skills/vc-self-check/deliver.mjs`, and `skills/vc-self-check/upstream-reduce.mjs` are **byte-identical** in `plugins/vc-fix/` and `.claude/`, so the hardened secret redaction + the default-deny closed-schema upstream path ship on BOTH — the client-data-leak class is closed on both, not just the distributed plugin. The `.claude/` mirror may still lag on **non-self-diagnostics** surface (e.g. no dedicated `/vc-feedback` command md — the `session-telemetry.mjs prompt` handler is present and wired, a shorter `skill-expectations.md`); those are prose/UX, not a containment gap. Self-diagnostics changes land in `plugins/vc-fix/` first and are copied to the mirror in the same change.

**The full `vc-qa` surface** (17 agents / 41 skills / 31 commands, plus its `knowledge/` and `hooks/`) is **no longer a plugin — it now lives under `.claude/`** (`.claude/agents/`, `.claude/skills/`, `.claude/commands/`, `.claude/knowledge/`, `.claude/hooks/`) as **project-scoped components** that Claude Code auto-discovers in *this* repo. This is the "normal project" layout: `/qa-*` and `/ba-*` commands load locally on any clone with no plugin manifest and no marketplace listing (the `.claude-plugin/plugin.json` manifest was deleted deliberately). The remaining code surfaces that consume these — `ci/` (headless pipeline), `scripts/`, `config/` — reference them at their `.claude/…` paths. It could still be re-packaged as a plugin later (a new `plugin.json` moving components back to the repo root + a `marketplace.json` entry) if the full-regression/BA offering is distributed; for now it is a plain in-repo toolset, not a distributable.

## Environment

Layered loader, keyed by `TEST_ENV` (default `vcst`). Validate: `npm run env:check`. Access: `import { env } from './config.js'`.

Load order (later overrides earlier): `.env.defaults` → `.env.${TEST_ENV}` → `.env.local` → legacy `.env` (backwards-compat fallback).

- **Per-env URLs/identifiers** (committed, no secrets): `.env.vcst` (current QA), `.env.vcptcore` (second QA), `.env.virtostart` (staging)
- **Secrets** (passwords, API tokens): `.env.local` only — gitignored
- **Cross-env constants** (sandbox cards, builder.io): `.env.defaults`
- Switch envs: `TEST_ENV=vcptcore npm run env:check` or `TEST_ENV=virtostart …`
- Agents read variable values via `process.env.X` — they don't care which file it came from. Variable *names* are stable across envs.
- ES modules project — always use `.js` extensions in imports
- URLs from env vars, never hardcoded. Default environment: vcst-qa
- **Frontend**: `FRONT_URL` | **Backend**: `BACK_URL` | **Storybook**: `STORYBOOK_URL` / `STORYBOOK_DEV_URL`
- Theme: Coffee | Communication: Microsoft Teams

## Repository Structure

Run `ls` — the layout is self-describing. Two non-obvious points `ls` does **not** show: `plugins/vc-fix/`
is the one distributed plugin and deliberately duplicates (rather than references) the root's
`knowledge/`/`rules/`/`config.js` — see §Project Overview for why; and `.claude/` is the project-scoped
`vc-qa` surface (commands/agents/skills/knowledge/hooks/rules), auto-discovered here with no plugin manifest.

**Gitignored:** `.env`, `.env.local`, `.env.backup`, `.mcp.json`, `results/`, `.newman-run/`, `.fix-workspace/`, `.vc-fix/` (self-diagnostics telemetry), `project-profile.json`, `.claude/settings.local.json` (note: `ci/` and `.github/` ARE tracked and ship with the plugin — only transient sub-paths like `ci/config/.module-registry.cache.json` are ignored). `.claude/settings.json` **is tracked** — it's the shared project config (hooks + `enabledPlugins`, incl. Serena); per-developer overrides go in the gitignored `.claude/settings.local.json` instead. **It deliberately does NOT register the self-diagnostics collector** (VCST-5582 H): `vc-fix@vc-tools` is enabled at the user level on the team's machines and ships its own `hooks.json`, so registering the `.claude/` mirror as well ran **two** collector processes per event against the same `.vc-fix/diagnostics/<sid>.*` files — duplicated spans and racing `saveState()` writes with lost cursor updates (observed: two `finalize` records 12 ms apart reporting 292 vs 290 spans). The mirror FILE stays (byte-identity is CI-enforced) and this repo now exercises exactly the copy a client runs; trade-off — a checkout *without* the plugin installed gets no telemetry here. `collector_contention` detection remains as a backstop for two parallel sessions on one `outputRoot`. **Serena dependency note:** `enabledPlugins.serena` only *enables* the official `claude-plugins-official`-marketplace Serena plugin for whoever has it installed (a no-op otherwise, never auto-installed) — when active it's a source-indexing LSP tool that runs against whatever gets checked out into `.fix-workspace/<repo>/`, which on a client deployment can be client code (§2a).

## Essential Rules

**Testing:**
- NEVER share a browser session between parallel agents — each gets its own isolated context
- Run deep/comprehensive tests unless explicitly told smoke. Always capture HAR files.
- Batch regression in groups of 3 (matching browser pool slots)

**Browser:**
- Use `chromium` (not `chrome`). WebKit NOT supported on Windows — use Edge fallback.
- Close Chrome windows before `playwright-chrome` (user data dir conflict)
- MCP config changes require server restart

**Agent Teams:**
- Mode: `teammateMode: "in-process"` in settings.json
- `post_edit` hook: `npx tsc --noEmit -p ci/tsconfig.json` (wired in `.claude/settings.json`; `typescript`
  is a devDependency). Its `include` covers `ci/*.ts` + `ci/lib/` + **all of `../scripts/**/*.ts`** — so
  every TS file under `scripts/` is gated. It was previously scoped to `../scripts/lib/*.ts` only, which
  silently left `scripts/deploy/`, `scripts/unit/`, `scripts/hotfix/` etc. unchecked: a green run said
  nothing about them. The config is typecheck-only (`noEmit`, no `outDir`) and sets
  `allowImportingTsExtensions` for the `tsx`-style `.ts` import specifiers the unit tests use.
  Max 3 concurrent browser agents.
- Browser assignments: see `.claude/rules/agents.md`

- **`/qa-test` is a command↔skill pair, not one file.** The command (`.claude/commands/qa-test.md`) is the **orchestration shell** — what runs, in what order, and the gate each step must clear; the **`/qa-test` skill** (`.claude/skills/qa-test/`: `SKILL.md` + `test-model.md` + `authoring.md` + `close-out.md` + `modes.md`, plus the shape in `.claude/templates/test-model.md`) holds the methodology and the measured rationale. Split 2026-09-01: at 1,044 lines it was the largest command in the repo and the only large one with no backing skill, so the pipeline contract, the methodology, the rationale and the worked examples were interleaved in one file — and a reader after "what runs at 5d" had to read past the Loyalty Missions evidence to find it. Same split as `/qa-design` ↔ `skills/qa-design/`. Two structural rules came out of it and are worth keeping: **the FAST path is stated once, completely, in one block** (it was 27 caveats scattered through FULL-path prose, so a FAST reader scanned the whole file to find the third that applied), and **everything after that block is the FULL path**. The command stayed normative and self-sufficient for *running* the pipeline — every gate's criteria are still in it, because they are the STOP conditions — while the skill answers *why*. `--epic` and `--iterate` moved wholesale into `modes.md`: two opt-in modes most runs never reach.
- **`/qa-test` is a tiered, gate-verified lifecycle** — Step `1a` **routes on two axes** (single source of truth: `.claude/knowledge/execution/ticket-routing.md`): first the **FLOW** by ticket **type × status** — a **fix-ready Bug** (READY FOR TEST/TESTING) is a *verification*, so `1a` runs `/qa-verify-fix` **RED→GREEN inline** (skipping the feature-test authoring/promotion machinery); a **hotfix-status Bug** → `/qa-hotfix-check`; a **Sub-task** → inherit its parent's type; everything else (Story/Task/Technical task/Epic, and a not-yet-fixed Bug) is a **`feature-test`**. Then, within `feature-test`, `1a` picks a **FAST or FULL path**, and the two now differ sharply in cost rather than marginally. **FAST is a checklist and nothing else**: a bug/tweak/config/tech-task that is P2–P3, single-layer and single-domain runs `1a`+`1b` → the Artifact-B checklist → one execution agent + the critical-case regression → `5a`–`5f`, with **no `1c`/`1d` agents, no `1e` Test Model, no archetype/UIP/`VC-*` sweeps, no case authoring, no `5g` promotion and no independent verifier**. The old split dropped only the two `1` agents and the verifiers while everything expensive stayed marked *"both paths, always"* — and 4 of the 5 recorded runs took FAST, so that was the path the cost sat on. Two consequences are deliberate: a FAST run **adds no regression coverage** (`/qa-test-lifecycle` is the way in), and its checklist is therefore the run's **only durable record**, which is why it is now a committed file. **FULL** — a new feature/Story/Epic, P0–P1, cross-layer, ≥2-domain, critical-revenue or unclear-surface ticket — runs the whole pipeline: `1c ‖ 1d` concurrent, **a mandatory Test Model**, full authoring, the three independent verifier gates, `5g` promotion. *When in doubt → FULL.* The **independent verifier runs only at the three hard-STOP gates (Step 3, Step 5b, Step 5g), FULL path only** — a **fresh `qa-lead-orchestrator` instance in §Verifier Mode** (`.claude/agents/qa-lead-orchestrator.md`), never the inline orchestrator and never the step's own doer: it re-derives evidence from source (re-runs `suites:review`/`td:validate`/`compute-metrics.ts --gate feature`, re-opens evidence, delegates a live re-check on a **different browser lane**), returns APPROVE/REJECT, and on REJECT gives reason + fix → the doer fixes → **re-verify once (1 round), then STOP**. Every other step + the whole FAST path self-check inline. Human stays terminal (TESTED/REOPEN + a GO/NO-GO recommendation). The Feature Release Gate's pass-rate/bug math is deterministic via `scripts/regression/compute-metrics.ts --gate feature`. **The Test Model (Step 1e) opens with the VALUE CHAIN and is a fault model, not a scenario list.** **Part 0 is derived first** (`/qa-test-design` `test-design-techniques.md` §1a, token `FLOW`): the chain stated one line per link in the user's words (`trigger → effect → persisted state → the surface the user sees it on → what it unlocks`), **drawn** in Mermaid (a `flowchart` always; a `sequenceDiagram` when the chain crosses layers or any part is async; a `stateDiagram-v2` when the entity has a lifecycle or an effect is expected to reverse), the feature's **variants** (goal types / processors / role kinds — different code paths through the same link, so matrix rows rather than input partitions), a **variants × links coverage matrix with no blank cells** (a scenario # or `GAP`/`WAIVED + reason` — a blank is a hole nobody can see), and **reverse edges** resolved per forward effect on money/points/stock/entitlement (covered by #, or `ABSENT IN PRODUCT`, which is a finding to report). Parts 1–5 then build the fault model **per link**: a `Condition space` (factors × value classes + constraints), an explicit `Reduction` rationale (`N → M`, naming the dropped factors and what subsumes them), and a scenario matrix whose every row carries **cell · defect hypothesis · archetype · technique · oracle** — its **first row being the `Technique:FLOW` journey** that traverses the whole chain on the customer's own surface, authored first by Step 3 and titled `[JOURNEY]` — plus (when the ticket has one) a DoD checklist. **The order is the point, not the paperwork.** EP/BVA/DT/ST/PW/CT/EG are all parameter-space techniques: they refine a link that has already been named and none of them can name the chain, so run against an unnamed chain they faithfully produce per-screen field checks that are individually well-formed, strongly asserted, and collectively unable to notice the feature does not work. Measured on Loyalty Missions (VCST-5320/5346): **127 cases**, of which the 71-case storefront suite placed **zero orders** and 54 of its cases never left one page; the mechanism end-to-end (order → progress → completion → points credited) got **11%**; the last link — spending what the feature grants — got **one** case, written on the final day; **zero `BL-*` invariants existed for the domain**, so the corpus recorded behaviour instead of judging it; and no model was written at all (`reports/ba/test-models/` was empty). `npm run tc:rank` scored that storefront suite as *strong* (41 `INV`, 58 `KEEP`) — assertion strength says whether a check **can fail**, chain coverage says whether anyone **cares if it does**, and only the second one culls a garbage case (`qa-test-cases-generator` Step 3 §6d: a case that neither crosses a chain link nor guards one the journey crosses, and §6's companion rule that **no case may invert its assertion to certify a known defect** — that makes it green today, unfalsifiable forever, and red the day the bug is fixed). Two tooling properties make *"if it looks stale"* unworkable rather than merely loose: **`loadSchemaCache` has no age check** (`scripts/lib/graphql-validator.ts`), so `npm run graphql:fixtures:validate` — the fixture gate — **passes clean against an arbitrarily old cache**, a false green with no warning line; and **the cache is one shared file, not one per env** (`scripts/.graphql-schema.cache.json`, hard-coded in three scripts), so a `TEST_ENV=vcptcore` run validates against whichever env refreshed it last — a mismatch the fixture library already records (`test-data/graphql/index.json` carries `backUrl` + `lastValidated`) and nothing was reading. The fix is **one derived token and two commands**, no new step and no new agent. `contract_surface` is derived beside `layer`/`visual_surface` (sources: the diff's `.graphql`/`*ExperienceApi*`/`*.Web/Controllers`/`*GraphType*` files → the derived `layer` = `api` → the target suites' `graphql`/`xapi` tags → an AC naming a query/mutation/response field; `storefront`/`admin-spa`/`platform` alone ⇒ `false`, **except** a `storefront` diff touching a `.graphql` document or a composable's query body, because the storefront is an xAPI *client* and a rename breaks it with no backend file in the diff; **`unresolved` ⇒ `true`**, the axis failing open on an asymmetry that is flatter than the visual one — a skipped refresh leaves the run reading a snapshot of unknown age, a needless one costs one introspection call, so there is no expensive direction). **TWO artifacts, TWO commands, and neither freshens the other** — this is the part that gets conflated (a line of `ba-api-specialist.md` claimed `schema:refresh` writes the cache; it does not, and that line is now corrected): `npm run schema:refresh` rewrites `knowledge/api/graphql-schema.md` **only** — the agent-facing oracle, whose own `> **Source**: … (YYYY-MM-DD)` header is the rev to quote — while `npm run graphql:fixtures:validate:refresh` re-introspects, writes the runner's cache, and validates all **74** fixtures, exiting non-zero on drift. **`npm run schema:check` is a liveness check, NOT a drift gate** (it renders and writes nothing, never comparing against the committed file), so unlike `tokens:check`/`selectors:check` it must never be cited as one. Three verdict rules: a failed refresh records **`UNKNOWN`** and **never** falls back to the committed snapshot (identical to `build.deployed`, for the identical reason), which downgrades every GraphQL oracle that would have been `{DOC}` to `{HYPOTHESIS}` — a state the provenance gate already forbids surviving promotion, so the run cannot quietly bank an ungrounded contract claim; **fixture drift is a Test Model INPUT before it is anything else** and splits by *whose* change caused it — an op the **ticket's own diff** touches is a `1e` finding (a moved contract is a value-chain link and a candidate reverse edge, and its OLD shape belongs in the regression scope), while drift elsewhere is recorded, cross-checked against `build.releasedThrough.breaking[]`, and **not chased** (that is `/qa-test-lifecycle`'s), and **neither files a bug from the gate alone** — a schema-validation failure is a claim about a *query document*, not about product behaviour, the same rule that makes a static-diff DRIFT at `1d` a suspicion; and a **skip is stated**, since an omitted contract block reads as a clean refresh. Two hand-offs are load-bearing, because refreshing a file nobody was handed changes nothing: the `1c`/`1d`/`1e` briefs carry the snapshot's **rev**, not its path (being handed a rev is what *removes* the staleness judgment instead of delegating it), and the 3b authoring pack is **cut from the refreshed file** — it is the fan-out's single point of contract failure, distributing one stale contract to every batch at once. It runs on **FAST as well as FULL** for the visual axis's own reason inverted: an xAPI field rename is *single-layer, single-domain, obvious surface, P2* by construction, so the change class that invalidates the contract is the class FAST routes — and unlike the visual lane this is not even an exception to FAST's one-execution-agent rule, because it dispatches no agent at all. Deliberately out: the REST/Swagger surface (no snapshot exists to refresh), oracle freshness (`/qa-review-oracles`' job — this axis refreshes *contracts*, never *invariants*), and **committing** the rewritten `graphql-schema.md` (git-tracked; the shared-tree rule forbids a tree-wide commit from a test run — report it, let a human commit). Record: `summary.json.contract` (`surface` + sources, per-artifact `refreshed`/`UNKNOWN`, and the two drift arrays kept apart so the in-scope/out-of-scope rule is auditable from the artifact). Single source of truth, cited and never restated: `.claude/skills/qa-test/contract-refresh.md`.

Step 2a then assigns every hit exactly one of four dispositions: `CONFIRMED` · **`REPAIR`** (the row is *mechanically* stale — a renamed selector, a moved route, a removed arg, a dead alias — so it cannot reach its own assertion; fixed **before** the run via `/qa-review-tests file <suite> --fix`) · **`RE-BASE`** (its *expected value* conflicts with the change; the assertion is kept **as it stands**, the case is carried into Artifact C on `--also-ids`, and 5a rewrites it afterwards with the run's own evidence) · `SUPERSEDED` (a proposal, never an edit — TRI-006 keeps retirement human and `tc:demote` may only reach `Manual`). **The `REPAIR`/`RE-BASE` split is the load-bearing rule and the reason this is not simply "update the stale cases":** the change under test is normally an **unmerged PR** (VCST-5733 tests three at once), so rewriting a case's expected value to match it *before* the run makes the change its own oracle — the case can then only pass, which is the `no case may invert its assertion to certify a known defect` failure arrived at from the opposite direction, and worse than the original because the rewrite happens in the run that reports the green. `REPAIR` is safe precisely because it moves the **mechanics** and not the **oracle** (and leaving it unfixed is not neutral — it manufactures a BLOCKED that reads as a product failure, the measured artefactual-BLOCKED class); a `RE-BASE` keeps **both** outcomes reachable, which is the whole point: fail + AC matches ⇒ the case was stale, fail + AC does not match ⇒ the case was right and it is a bug. Two hard rules: a `FILTERED_OUT` row disposed `RE-BASE` **must** appear on `--also-ids` or be re-dispositioned with a reason (an undisposed `RE-BASE` that never runs re-creates the exact gap inside the mechanism built to close it), and **Step 2a files no bug** — a hit is a claim about a *test case*, never about the product, the same rule 2d applies to contract drift. `never_audited` is context, not a verdict (TRI-000 answers *when*, never *whether*). Record: `summary.json.coverage_triage` (the `tc:scope` arguments used, so the Step-3 verifier re-runs the identical scan; per-disposition counts; and the `RE-BASE` ids carried into Artifact C). Single source of truth, cited and never restated: `.claude/skills/qa-test/coverage-triage.md`.
