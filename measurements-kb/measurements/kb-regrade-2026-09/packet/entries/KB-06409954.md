There is no single flag. A blocked member is represented in THREE independent places and no door writes all three, so the surfaces disagree in both directions. (1) The contact's own status - what the storefront roster and its row menu read. (2) The security account's Status enum, the dropdown on the Admin account blade, observed as Approved / Locked / PendingApproval. (3) The account's lockout, shown on the same blade as the derived read-only Locked state and toggled by the Lock/Unlock account toolbar button. Blocking through the storefront (Mutations.lockOrganizationContact) sets contact status to Locked and the account lockout to Locked, but leaves the account Status enum at Approved - so Admin then shows a locked-out user whose Status field still reads Approved. Locking through Admin sets the lockout, and setting the Status dropdown sets the enum, but neither touches the contact status - so the storefront roster still renders the member Active with a green tick and its row menu still offers Block user rather than Unblock user. Consequence for anyone asserting on member state: name which of the three you mean, because 'blocked' is not one fact. The lockout is the one that governs sign-in; the other two are labels that can lag it indefinitely in either direction.
