UserType.lockedState (Boolean, 'Account locked state') is the field that answers it, and it is reachable from the storefront schema on ContactType.securityAccounts, which returns [UserType]. UserType also carries lockoutEnd, lockoutEnabled and accessFailedCount. This matters because a page can select the account object and still show nothing true about it: the company members roster selects securityAccounts{id,email,roles} and omits lockedState, which sits on the type it is already querying - the truthful value is one field name away, not absent from the API. The contact's own status field is NOT a substitute: it describes the member record, not the account, and stays Approved for an account that is Locked or PendingApproval. Anyone asserting on whether a member can sign in should select securityAccounts{lockedState} rather than inferring it from contact status.
