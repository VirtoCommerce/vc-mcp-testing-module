## What you are doing

A real QA task against a Virto Commerce deployment, using the knowledge base as you go and
recording what you learn. **The QA task is the job.** The base is a tool you use and feed; it is
not the subject of the work, and you are not testing it.

Your session is instrumented. Three logs are written for you and one by you:

* `MEASUREMENT/tool-log-<session>.jsonl` — every tool call, written by a hook. Automatic.
* `MEASUREMENT/kb-log-<session>.jsonl` — every `kb` invocation. Automatic.
* `demand.jsonl`, beside the base — every question you put to it, and every observation it served
  you. Automatic, and it is **not** part of the measurement: it belongs to the base and outlives
  this run. See "The loop" below.
* `MEASUREMENT/questions-<session>.csv` — one row per question. The `kb` door adds the row when
  you consult the base; **you close it** (below).

The base may also speak without being asked. A hook watches what you touch, and when you land on a
coordinate it has an entry about — a route, a page, a GraphQL type — it hands you that entry. You
did not ask for it and you are not obliged to read it; it is there because three previous runs
consulted the base in their first three minutes and then worked for an hour and a half without
opening it once.

## Signing in — the lane matters

The storefront and the Admin SPA both sit behind a login form, and both are in scope.

**Use the `playwright-chrome` lane for anything authenticated.** It runs with
`--secrets`, so you sign in by typing the secret's **NAME**, not its value:

```
browser_type(text="B2B_USER_PASSWORD")     # the NAME, verbatim
```

The MCP server substitutes the real value on its way to the page and redacts it from its own logs,
so nothing you TYPE is ever a credential. Substitution fires only when the typed text is exactly a
name in the secrets file. Available names include `USER_EMAIL`, `USER_PASSWORD`, `ADMIN_PASSWORD`
and `B2B_USER_PASSWORD`.

**The redaction covers what the server writes, not what its network inspector hands back.** Run 02
found this: `browser_network_request` with `part: "request-body"` returned the sign-in POST with the
password in plaintext, and `part: "request-headers"` returned the full bearer token. Both landed in
that run's context, from one call, after it had correctly typed only names.

So, on any authenticated flow: **read response bodies only.** Never ask for `request-body` or
`request-headers` on a request that carries a credential — the sign-in POST, and every call after
it that carries an `Authorization` header. If one comes back anyway, say so in your report; do not
quote it, do not paste it anywhere, and do not put it in a note or a capture.

You never open the secrets file and you do not need to: the MCP server reads it at startup, and
naming a key that is not in it simply types the literal string and fails the sign-in, which tells
you what you need to know. It is scoped to login passwords alone — deliberately not `.env.local`,
which also holds API tokens, so that no page and no injected instruction can talk a browser lane
into typing a PAT into a form.

**This works on `playwright-chrome` and nowhere else.** `--secrets` is a `@playwright/mcp` flag.
On the built-in browser, on `claude-in-chrome`, and on Chrome DevTools MCP there is no
substitution: typing a NAME submits the literal string, the sign-in is refused, and an auth-gated
route bounces you to the login page. The first run of this measurement lost the whole UI half to
exactly this — it drove the built-in browser, met a login form, and correctly declined to type a
password, while the lane that could have signed it in was never called.

So: authenticated UI work goes through `playwright-chrome`. If you find yourself about to type a
password value rather than a name, stop — you are on the wrong lane.

**The sign-in that works on this deployment**, so you do not spend attempts finding out: the
storefront takes the address in `IMPERSONATION_ADMIN_EMAIL` — read it from `.env.defaults`; it is a literal, not a
secret — with the secret name `IMPERSONATION_ADMIN_PASSWORD`. It lands as a Customer of an org that
already has a usable shipping address. `USER_EMAIL` with `USER_PASSWORD` or `B2B_USER_PASSWORD` is
refused: that contact's only account has a different username and is of type Manager, so the form
posts a username with no login and the error is a generic `login_failed` whatever the password.

This is written here rather than left for you to rediscover because run 02 spent three refused
attempts on it and stopped rather than risk a lockout, and because it is a condition of the
experiment rather than a fact about the platform — stating it in the brief keeps it visible to
anyone reading the measurement, instead of reaching you through a side channel nothing records.

You can also ask whether a secret name exists without submitting anything: type the NAME into any
harmless text field and read the echoed Playwright code. `fill(process.env['NAME'])` means the key
is in the file; `fill('NAME')` means it is not. No submit, no failed sign-in, no lockout counter.

## The protocol

**1. Set the phase.** The question log has a `phase` column, the door cannot know it, and nothing
is defaulted — so a question asked with no phase set is not recorded at all. Export it and update
it as the work moves:

```
export KB_PHASE=orient      # then locate · understand · reproduce · change · diagnose · verify · restore · report
```

**2. There is a knowledge base in this repository.** `node bin/kb.mjs --help` explains it. In
short: `deliver "<question>"` answers a question about the platform from it or says `KB MISS`, and
`capture` puts something into it. Anything you ask through `deliver` lands in the CSV as a row for
you to close at step 3, and on the base's own books until something is written back about it.

It answers two KINDS of question with two verbs, and neither can reach the other's corpus:
`deliver` answers what is TRUE, and `how "<what you are trying to get done>"` answers what to DO,
in order. `capture --flow` records a procedure, with `--subject` stating the GOAL rather than the
actions.

Two things about it that are true whether or not you use it. It rarely misses — across three
previous runs it was asked 23 questions and missed none — and missing is not the same as answering:
one of those runs was served a generated type table for a question that needed something else, and
had to go and find that something else itself. So if you do ask it, step 3 is where you say which
of the two happened.

Use it, or do not, as the work suits you. This paragraph is deliberately not an instruction.

**3. Close the row when you know the answer.** This is the half the door cannot write, and it is
where most of the value is:

```
node vendor/agent-log/log-row.mjs mark --row <n> \
  --answer "what turned out to be true" \
  --held HELD|CONTRADICTED|NOT-USED|UNANSWERED \
  --found-elsewhere yes|no \
  [--found-via "where it actually came from"] [--note "..."]
```

`--held CONTRADICTED` when you acted on the base's answer and it did not survive contact with the
system. Say so plainly; a contradicted answer is the single most useful row in the file.

This row and the base's own loop are two different things and both are wanted. The CSV row is the
measurement — it records what turned out to be true and where you really found it, and only you can
write it. The loop is the base's own memory of an unanswered question, and it settles itself when
you capture (step 4) or when you say there was nothing to capture.

**4. Record what you learned.** When you find out something about the platform that was not
already in the base and that a later run would want:

```
node bin/kb.mjs capture \
  --subject "short-stable-noun-phrase" \
  --question "the question this answers, in an asker's words" \
  --claim "the fact itself" \
  --refutable-by observation \
  --anchor "POST /some/route" [--anchor "Type.field"] \
  --scope "surface=..." [--scope "principal=..."] \
  --deployment vcptcore_stable
```

Nothing is defaulted, so the door names anything you left out. It may also **refuse** with exit 4
— the base already holds a fact under those coordinates at that scope — and the message says what
to do instead.

**What belongs in each field, and what is not worth recording at all, is on the verb's own help
page:**

```
node bin/kb.mjs capture --help
```

Read it before your first capture. It is the only copy of that guidance, and it deliberately does
not live in this brief: the brief is scaffolding for the measurement and dies with it, while the
decision it informs — is this worth another agent's time? — is made every time anyone writes to
the base, long after no brief is in play.

**Anchor on where you actually were.** If you found it out by calling a route or by working on a
page, anchor it on that route or that page as well as on any type involved. This is what lets the
base reach the next run at the moment it arrives there, and it is measured: the derived plane's 590
entries are anchored on GraphQL type and field names, which appear in no browser URL, so they
contribute almost nothing to that. Two entries in the whole base are anchored on a storefront path.

## The loop

The base keeps every question you put to it until something is written back. One line appears under
any `kb` command when something is open, and the list is:

```
node bin/kb.mjs demand
```

Three things close a row, and all three are legitimate:

* **a capture using the SAME question wording** — that is the match, deliberately, rather than
  anchor overlap. A capture anchored on `Query.cart` closing every open question that ever
  mentioned the cart would delete the demand signal while the gap was still there.
* **`kb confirm <id>` or `kb dispute <id>`** — for an observation the base served you.
* **`node bin/kb.mjs demand drop <key> --reason "..."`** — when you found out and it was not worth
  an entry. That is a real outcome, said plainly, and the loop needs somewhere to put it. It is
  recorded rather than erased.

**Do not leave the loop to the end.** Three runs wrote every one of their entries in the closing
report, from memory — run 03 wrote four in thirty-nine seconds at 83% through. Anything those runs
learned and then superseded was never written at all. Close a row when the question closes, not
when the work does.


## When the base serves you another agent's observation

Most of what the base holds is generated from the deployment and cannot be wrong about a signature.
A few entries are different: they were written by an agent that observed something, and the
delivered block says so — `single-observation` or `confirmed`, with a count and the scope axes it
was seen under, rather than `derived from the deployment contract`.

Those are the ones worth acting on carefully, because they are beliefs and not projections. When
you use one and it holds, say so; when it does not, say so louder:

```
node bin/kb.mjs confirm <ID> --deployment vcptcore_stable
node bin/kb.mjs dispute <ID> --deployment vcptcore_stable --note "what you saw instead"
```

A confirmation is not bookkeeping — it is the only thing that moves an entry from one agent's
report to something two runs have seen, and it is what lets a later reader tell the difference. A
dispute leaves the entry in place and served, at trust level `disputed`, with both sides visible;
hiding a contested fact hides the contest.

If a served entry says it was `OBSERVED ELSEWHERE`, it was recorded on a different deployment from
the one this base describes. It may still be right. It has simply not been seen here, and one
confirmation from you is what changes that.

This applies to an entry that arrives on its own as much as to one you asked for. When the hook
hands you something marked `written by an agent`, it is one person's observation about a coordinate
you are standing on — the most useful thing in the base and the least certain. Use it and say
whether it held. Nobody in three runs has ever confirmed an entry they were served without being
reminded, which is why the base now reminds you.

## What to record, and what not to

`node bin/kb.mjs capture --help`. In one line: a fact about **the platform** that you had to find
out, stated as the MECHANISM rather than the instance, so that it is still right on a deployment
you have never seen. A procedure counts and a diagnosis counts — if you got stuck and worked out
how to get unstuck, that is often worth more to the next agent than the fact you were after.

If you learn nothing worth recording, record nothing. A run that captures zero facts is a result,
not a failure — and it is one this measurement genuinely wants to be able to see.

## At the end

```
node vendor/agent-log/log-row.mjs check          # rows still open, and rows that claim a lookup at an unmoved call count
node vendor/agent-log/reconcile.mjs MEASUREMENT  # the two logs side by side
node bin/kb.mjs demand                           # open questions, unconfirmed observations, shared coordinates
node bin/kb.mjs consolidate                      # entries that a reader will be served together
```

**Read the consolidate groups.** They are not defects: two entries about one coordinate are usually
two honest facts about one place. What makes them worth a minute is that anyone asking about that
coordinate is served *every* member of the group — so if two of them disagree, one is teaching the
next agent something false. A previous run wrote two entries nine minutes apart on `/company/members`
and the second quietly refuted a clause in the first; nobody noticed for a day.

If one of yours turns out to be wrong, do not leave both served:

```
node bin/kb.mjs supersede <id> --reason "why it stopped being true"   --subject … --question … --claim … --refutable-by … --anchor … --scope … --deployment …
```

It writes the new fact and retires the old one in one act. The old id stays resolvable and keeps
your reason plus a pointer to the replacement, so a report that cited it still leads somewhere true.

`kb demand` should be empty, or every remaining row should be one you can say a sentence about in
your report. An open row is not a failure — it is a question this base cannot answer and now knows
it cannot, which is worth more than a tidy list.

Then report, in your own words: what the task needed, what the base gave you, where it was wrong or
missing, and what you recorded. Do not grade yourself — someone who has not read your journal does
that.

One thing to say explicitly, because it is what this run exists to find out: **when did you touch
the base, and why then?** The three runs before you consulted it inside their first three minutes
and then worked for over an hour without opening it, and wrote everything they recorded in the
closing report from memory. If you did the same, say so plainly — that is the result. If something
pulled you back to it mid-task, say what.

## Before you write the report, gate what you wrote

```
node bin/kb.mjs validate
```

One command, needs no deployment, and it is the difference between leaving a corpus that works and
leaving one that does not. **This was not in the brief until run 07**, which wrote an entry whose
anchor Git Bash had rewritten into a path inside its own installation, and left the base failing its
gate. The run did nothing wrong: it was never asked. Nobody had noticed the rule lived only in the
author's head.

`VALIDATE OK` and you are done. A problem names the file and what is wrong with it; fix it and run
it again. The notices underneath are not problems — they are anchors nothing can raise, printed on a
green run too, and an observation about a surface this base does not project is expected to be
there.
